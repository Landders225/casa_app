# CASA — Décisions d'architecture (ADR)

Lot 0. Chaque entrée : contexte → décision → conséquence. Numérotées, jamais renumérotées (une décision annulée est marquée `[REMPLACÉE PAR ADR-xx]`, pas supprimée).

---

## ADR-01 — Authentification : Sanctum SPA (cookies same-origin)

**Contexte.** Frontend React SPA séparé du backend Laravel, mais destiné à être servi depuis le même domaine public via le reverse proxy nginx (règle imposée).
**Décision.** Laravel Sanctum en mode SPA (cookie de session, pas de token Bearer exposé au JS). `SANCTUM_STATEFUL_DOMAINS`/`SESSION_DOMAIN` alignés sur le domaine public unique servi par nginx.
**Conséquence.** Pas de jeton d'API stockable côté client (moins de surface d'attaque XSS/exfiltration) ; toute requête API doit passer par le même domaine que le frontend (contrainte sur le déploiement — un seul point d'entrée nginx, cf. docker-compose.yml). CSRF cookie (`/sanctum/csrf-cookie`) à récupérer avant toute requête mutante — à implémenter au lot d'authentification.

## ADR-02 — Scoring 100 % serveur, jamais dans le bundle ni une réponse API candidat

**Contexte.** Règle non négociable 1. Dans la maquette, `scoring.js` est chargé par **toutes** les pages, y compris candidat (masquage a posteriori par `casaCandidatPourAffichage()` côté client — une dette qu'on ne reproduit pas).
**Décision.** Le barème (`grille`, `volet`, `rubrique`, `item`, `option_item`, `sous_critere_entretien`, `critere_priorite`) et toute la logique de calcul (`ServiceScoring`, `ServiceEligibilite`, `ServiceClassement`) vivent exclusivement côté backend Laravel. Aucun de ces éléments n'est sérialisé dans une réponse API atteignable par le rôle `candidat`, ni présent dans le bundle React.
**Conséquence.** Toute API Resource candidat doit être écrite par liste blanche de champs (jamais `Resource::make($model)` générique sur `candidature`/`evaluation_dossier`) et revue contre la checklist confidentialité de `docs/dictionnaire-donnees.md`. Un test automatisé (lot ultérieur) doit vérifier qu'aucune route accessible à `candidat` ne peut retourner une colonne 🔴.

## ADR-03 — Statut public dérivé exclusivement côté serveur (statut interne ≠ statut affiché)

**Contexte.** Exigence explicite du Lot 0 : ne pas reproduire `casaCandidatPourAffichage()` comme fonction de masquage côté client. `candidature.statut_interne` peut valoir `non_eligible`/`evalue`/etc. avant toute publication ; le candidat ne doit voir qu'un statut neutre jusqu'à publication.
**Décision.** `statut_interne` **n'est jamais stocké en double** sous une forme "publique" (pas de colonne `statut_public` redondante, source de désynchronisation possible). À la place, un composant serveur unique et non contournable — `StatutPublicResolver` (service applicatif, invoqué par une API Resource dédiée `CandidatureCandidatResource`) — calcule le statut affichable à la volée, à partir de `statut_interne` + existence de `publication` sur la campagne :

| `statut_interne` | `publication` existe ? | `statut_public` renvoyé |
|---|---|---|
| brouillon / soumis / en_instruction / non_eligible / evalue | non | `en_cours_de_traitement` (toujours, sans exception) |
| n'importe lequel | oui | `decision_publiee` + `decision_candidature.decision` |

`decision_candidature.rang` et `.motif_interne` ne sont **jamais** lus par ce composant. `.motif_communicable` n'est lu et exposé que dans la branche "publication existe", et seulement s'il est non nul (sinon message générique **fixe côté client**, pas une donnée serveur).
**Conséquence.** Aucun contrôleur candidat n'a le droit d'accéder directement à `candidature.statut_interne` ou `decision_candidature` — seul `StatutPublicResolver` le peut, et il est le seul composant testé pour cette dérivation (un seul endroit à faire évoluer si la règle change). Illustré en détail dans `docs/uml-sequences.md`, séquence (c).

**Implémentation (Lot 5b — publication & résultat candidat).** `StatutPublicResolver::resoudre()` renvoie désormais un VO `StatutPublicCandidat` (`statutPublic`, `decision`, `motifCommunicable`). Table de vérité : `brouillon` → `brouillon` ; sinon **sans `publication`** → `en_cours_de_traitement` (décision cachée, quelle que soit sa valeur) ; **avec `publication`** → `decision_publiee` + `decision_candidature.decision` (ou `non_retenu` si la candidature n'a jamais été classée — soumise sans entretien, ou éliminée à la soumission) + `motif_communicable` (nullable → message générique **fixe côté client**). La branche « publication existe » fait un `SELECT` explicitement limité à `decision, motif_communicable` : **`rang` et `motif_interne` (🔴) ne sont jamais chargés**. `CandidatureCandidatResource` gagne exactement deux clés en liste blanche : `decision` et `motif_communicable` (toutes deux `null` avant publication).

**Acte de publication.** `POST /api/admin/campagnes/{campagne}/publier` (administrateur strict) : **acte notarial, pas un calcul** — aucun recalcul, on gèle la visibilité sur l'état du dernier `POST .../classement` que l'admin a relu. Garde-fous : ≥ 1 `decision_candidature` (sinon 422) ; **irréversible** (re-publier → 409, aucune dé-publication ; le classement n'est plus recalculable — cohérent 5a). `INSERT publication` + `journal_audit` « Publication des résultats ». Le split calc / publication (2 actes distincts) diverge de la séquence (c) qui les bundle — cohérent avec **D-5a-2**.

**D-5b-1 (divergence maquette assumée — la règle reine prime).** `ma-candidature.html` (l.78-79) affiche, APRÈS publication, une bannière « Candidature non éligible » avec le motif d'échec d'éligibilité pour un `statut === 'non_eligible'`. Cela **viole** la règle 1 / le contexte §16-17 (le candidat n'apprend jamais la cause interne). Le backend applique la règle : un `non_eligible` (décision `non_retenu` + `motif_interne = 'non éligible'` du Lot 5a) voit **exactement** un `non_retenu` générique — `StatutPublicResolver` ne lit ni `statut_eligibilite_interne`, ni `motif_interne`, ni `critere_eliminatoire_declenche`. Quand `motif_communicable` est `null` des deux côtés, la réponse `GET /api/candidature` est **byte-identique** à celle d'un `non_retenu` ordinaire (test dédié `test_INDISCERNABILITE_non_retenu_ordinaire_vs_non_eligible`). La maquette reste source de vérité pour les écrans/flux, jamais au-dessus de la confidentialité.

## ADR-04 — Score figé (snapshot) + grille versionnée

**Contexte.** Le barème doit être administrable en base (règle 6), donc modifiable dans le temps. Une évaluation déjà verrouillée ne doit jamais changer de valeur suite à une modification ultérieure de la grille.
**Décision.** `grille` est versionnée (`version`, `actif`) ; `evaluation_dossier`/`entretien` référencent la version exacte utilisée (`grille_id`) et stockent un `score_total` **figé** au moment de la validation, ainsi qu'un détail par rubrique (`score_rubrique_dossier`/`note_sous_critere_entretien`). Le recalcul serveur (`ServiceScoring`) ne s'exécute que pour un dossier **non verrouillé** (brouillon d'évaluation) ou lors d'une correction exceptionnelle explicite (qui produit un nouveau snapshot, tracé à l'audit).
**Conséquence.** Changer la pondération d'une rubrique n'affecte que les évaluations futures. Un audit "que se serait-il passé avec l'ancien barème" reste possible en conservant `grille_id` sur chaque évaluation historique.

**Implémentation (Lot 4c — volet Entretien).** Même schéma que le 4b. `note_sous_critere_entretien` = sous-notes brutes (12 — cf. D-4c-4), mutables tant que `entretien.statut != 'valide'` ; `GET .../entretien` renvoie un **aperçu** recalculé sur la grille active. À la validation (`POST .../entretien/validation`) : `entretien.statut = 'valide'`, `score_total` (/35) + `grille_id` figés, les **12** `note_sous_critere_entretien` figées (0 pour un sous-critère non renseigné, ou tous à 0 si `presence = 'absent'`), ligne `journal_audit` « Validation d'entretien » (module « Entretien »). Après : `PUT` / `POST .../validation` → **409** ; `GET` → snapshot figé, jamais recalculé (grille v2 activée ⇒ score inchangé — test dédié). Précondition : `candidature.dossier_verrouille = true` (le dossier /65 doit être validé) — **409** sinon. **D-4c-1** : le verrouillage entretien vit sur `entretien.statut = 'valide'` (pas de colonne dédiée sur `candidature`) ; `candidature.statut_interne` reste `evalue` (l'avancement fin sur la table spécialisée, comme la vérification au 4a ; `rankCandidatsParFiliere` de `scoring.js` filtre sur `entretien.statut`). **D-4c-2** : la planification portée par `PUT .../entretien` (date / heure / lieu) est *minimale* — la gestion complète (convocations, calendrier, replanification) est un lot administration (la maquette : « Phase C »). **D-4c-3** : `CHECK (lieu IN ('Le Plateau','2 Plateaux Vallons'))` ajouté sur `entretien` (le MLD ne le citait qu'en commentaire). **D-4c-4** : le volet Entretien compte **12** sous-critères (PRES/REL/EO/MOE × 3), pas « 10 » comme l'écrivaient le cahier des charges du lot et un commentaire du MLD — la source de vérité est `scoring.js` (`CASA_GRILLE`) ; Σ des maxima = 8+10+8+9 = 35. **Divergence de vocabulaire signalée** : les libellés de `entretien.lieu` (`Le Plateau`, `2 Plateaux Vallons`) désignent les deux mêmes sites que les items d'éligibilité DI.04 / DI.05 (`acces_plateau` / `acces_deux_plateaux_vallons`, formulés « au Plateau » / « aux 2 Plateaux Vallons ») — types différents (énum texte vs booléens), aucun couplage technique.

**Implémentation (Lot 4b — volet Dossier).** Tant qu'une évaluation n'est pas validée : **aucune ligne `evaluation_dossier`** ; `GET .../evaluation` renvoie un **aperçu** recalculé à la volée par `ServiceScoring` sur la grille active (`source: "apercu"`). À la validation (`POST .../evaluation/validation`) : `evaluation_dossier` (`score_total` /65, `valide=true`, `valide_par`, `valide_le`) + les **6** lignes `score_rubrique_dossier` + `grille_id` de la grille alors active, dans une transaction ; puis `candidature.dossier_verrouille=true`, `dossier_verrouille_par/le`, `statut_interne='evalue'`, `date_evaluation`, et une ligne `journal_audit` « Validation d'évaluation ». Après verrouillage : `GET .../evaluation` renvoie le **snapshot** figé (`source: "snapshot"`), jamais un recalcul — même si une grille v2 est activée ensuite ; `PUT .../evaluation` et `POST .../evaluation/validation` répondent **409** ; `PUT .../verification` (Lot 4a) aussi (garde `statut_interne === 'en_instruction'`). La ré-ouverture est réservée à la correction exceptionnelle admin (lot ultérieur). **D-4b-1** : `score_rubrique_dossier.score_obtenu` élargi de `numeric(4,2)` à `numeric(6,4)` — `scoring.js` produit des décimales périodiques pour `experience` / `langues` (ex. 6/9×10 = 6,6667) ; `score_total` reste `numeric(4,1)`, arrondi comme `scoring.js`.

## ADR-05 — Réponses brutes et sous-notes persistées séparément et intégralement

**Contexte.** Exigence explicite : le score par rubrique seul ne suffit pas pour permettre un recalcul serveur ou un audit ancienne/nouvelle valeur.
**Décision.** `reponse_formulaire` (1-1 candidature) porte **tous** les champs bruts du formulaire (SC.\*, SE.\*, DI.\*, langues, informatique). `note_sous_critere_entretien` porte les 12 sous-notes d'entretien individuellement (cf. D-4c-4), séparément du score agrégé stocké sur `entretien.score_total`. Ces deux tables sont🔴 mais restent la source que `ServiceScoring` relit pour tout recalcul (correction exceptionnelle notamment).
**Conséquence.** Une correction exceptionnelle peut modifier un champ précis (ex. `di02_contraintes`) et ne recalculer que ce qui en découle, avec une trace exacte "ancienne valeur → nouvelle valeur" au niveau du champ, pas seulement du score agrégé.

## ADR-06 — Élimination : logique serveur versionnée, pas de moteur de règles générique

**Contexte.** Le barème doit être en base (règle 6), mais la logique d'élimination (bornes d'âge, groupe OR sur les 2 sites, seuil de français...) est un algorithme, pas une simple donnée.
**Décision.** `ServiceEligibilite` est codé et testé côté serveur (versionné par le déploiement de code, pas par une table de règles génériques). Chaque candidature trace les critères **effectivement déclenchés** dans `critere_eliminatoire_declenche` (miroir de `motifsElimination` de la maquette), avec un champ `origine` distinguant ce qui est connu dès la soumission candidat de ce qui n'est connu qu'après vérification évaluateur (nationalité, diplôme).
**Conséquence.** Modifier une règle d'élimination (ex. changer le seuil de français) nécessite un déploiement de code (revue, tests), pas juste une modification en base — choix assumé pour la fiabilité, au prix d'un peu moins de souplesse admin sur ce point précis.

**Implémentation (Lot 4c — scoring entretien).** `ServiceScoring::calculerEntretien` — portage fidèle de `scoring.js` `computeEntretienScore()` : chaque sous-note bornée à `[0, sous_critere_entretien.max_points]` (**lu en base**), somme par rubrique (pas de plafond rubrique séparé), somme des rubriques plafonnée au `max_points` du volet, arrondie à une décimale. **Aucune constante algorithmique** (pas de rééchelonnage). Un sous-critère non renseigné vaut **0** (`rNotes[sc.code] ?? 0`). `points_attribues` reste `numeric(3,1)` (demi-points admis) — pas de perte de précision, `score_total` `numeric(4,1)` exact.

**Implémentation (Lot 4b — scoring).** `App\Domain\Scoring\ServiceScoring` (`VERSION = 1`) applique la même règle qu'`ServiceEligibilite` : portage **fidèle** de `scoring.js` `computeScores()` (volet Dossier /65), **barème lu en base** sur la grille passée en argument (poids de rubrique, points d'option, max d'item) — aucune valeur de barème en dur. Seules les **constantes algorithmiques** de `scoring.js` vivent dans le code : domaines d'expérience reconnus, `moisApprox` (3/9/15) et seuils de durée (12, 6), échelle des niveaux langue (0-3), échelle des étoiles (0-5), et la table `item.code → colonne reponse_formulaire`. Le rééchelonnage langues /9→/10 est algorithmique (le dénominateur 9 = somme des `item.max_points` LANG.FR + LANG.INFO). Ce que l'évaluateur saisit et qui entre dans le calcul : `reponse_formulaire.mo04_note_etoiles` (Lot 4b) et `verification_dossier.diplome_verifie` (Lot 4a, pour SC.04). **D-4b-2** : l'évaluateur ne réajuste PAS les autres réponses candidat pendant la notation (la maquette `evaluation.html` le permet) — corriger une déclaration candidat passe par la correction exceptionnelle admin (motif obligatoire, tracée), lot ultérieur. **D-4b-3** : la validation ne relance PAS `ServiceEligibilite` (la maquette le fait) — ses entrées (réponses candidat, vérification 4a) n'ont pas changé depuis les Lots 3c / 4a, un re-run serait un no-op ; `statut_eligibilite_interne` n'est pas touché par 4b. Un dossier `non_eligible` **peut** être noté (le score est un fait ; le classement filtrera).

**Implémentation (Lot 3c).** `App\Domain\Eligibilite\ServiceEligibilite` (`VERSION = 1`), portage fidèle de `scoring.js` : `evaluerSoumission()` ⇔ `checkCriteresEliminatoires` (10 critères connus à la soumission, `origine='soumission_candidat'`), `evaluerVerificationEvaluateur()` ⇔ `checkCriteresEliminatoiresEvaluateur` (SC.04 CEPE, nationalité — `origine='verification_evaluateur'`, **non appelé** au Lot 3c faute de `verification_dossier`). Âge calculé à `campagne.date_ouverture` (référence fixe pour la cohorte). Chaque critère est inséré individuellement dans `critere_eliminatoire_declenche`. La séparation complétude / éligibilité est stricte : `ValidateurCompletude` (dicible, 422 détaillé) ne lit aucun critère, `ServiceEligibilite` ne s'exécute qu'après une complétude OK, et **son résultat n'apparaît dans aucune réponse candidat** (règle reine, séquence a).

## ADR-07 — Nationalité et diplôme : uniquement dans `verification_dossier`

**Contexte.** Fidélité au flux réel de la maquette (`inscription.html` : `nationalite: null` à la création) — aucun de ces champs n'est jamais auto-déclaré par le candidat.
**Décision.** Aucune colonne nationalité/diplôme sur `candidat` ou `reponse_formulaire`. Seule `verification_dossier.nationalite_confirmee`/`.diplome_verifie`, saisie par un `membre_equipe`, fait foi.
**Conséquence.** Le formulaire candidat (frontend) n'a structurellement aucun champ à afficher pour ces deux informations — cohérence garantie par le modèle, pas seulement par l'écran.

## ADR-08 — Publication rattachée à la campagne (pas de flag global)

**Contexte.** La maquette utilise un flag applicatif unique (`CasaPublication`), simplification permise par l'absence de campagnes concurrentes dans la démo.
**Décision.** `publication` est 1-1 avec `campagne` (une campagne = au plus une publication). `StatutPublicResolver` (ADR-03) résout la visibilité **par campagne** de la candidature concernée, pas globalement.
**Conséquence.** Plusieurs campagnes peuvent coexister avec des publications indépendantes (ex. Cohorte 1 publiée pendant que Cohorte 2 est encore en cours d'évaluation).

## ADR-09 — Quota porté par `campagne_filiere`, pas par `filiere`

**Contexte.** Idem ADR-08 : la maquette modifie `cqp.quotaParCohorte` comme un attribut permanent de la filière.
**Décision.** Le quota est un attribut de l'association N-N `campagne_filiere`, pas de `filiere` elle-même.
**Conséquence.** Une même filière peut avoir un quota différent d'une cohorte à l'autre sans conflit.

**Implémentation (Lot 5a — classement & décisions internes).** `App\Domain\Classement\ServiceClassement` (`VERSION = 1`), portage fidèle de `scoring.js` (`computeScoreFinal` + `rankCandidatsParFiliere`) et de `classement.html` (`computeRanking`). **Quotas lus en base** (`campagne_filiere.quota`) ; **score final /100 = somme des snapshots figés** `evaluation_dossier.score_total` + `entretien.score_total` (ADR-04), plafonné à 100, arrondi 1 décimale — **pas** un recalcul des volets (la maquette recalcule via `computeScores`/`computeEntretienScore` faute de snapshot). Inclusion : `dossier_verrouille = true` ET `entretien.statut = 'valide'`. Tri : score final, puis départage **ordre exact scoring.js** — mixité (F) > vulnérabilité NEET (`vulnerabiliteScore`) > expérience secteur hôtellerie-restauration > motivation (`mo04`) — **puis D-5a-1**. Décision : `rang ≤ quota` → `retenu` ; `≤ quota + 8` → `liste_attente` ; sinon `non_retenu`.

- **D-5a-1** : départage FINAL déterministe ajouté (`date_soumission` croissant, puis `candidature.id`). `scoring.js` s'appuie sur la stabilité du tri JS (ordre d'insertion) en cas d'égalité sur les 5 critères ; on rend le résultat reproductible.
- **D-5a-2** : `decision_candidature` (`rang` 🔴, `decision` 🟡, `motif_*`) est **persistée dès le Lot 5a** (calcul du classement), alors que la maquette ne l'écrit qu'à la publication. Aucune `publication` n'est créée ici ⇒ `StatutPublicResolver` inchangé, le candidat ne voit toujours que `en_cours_de_traitement`. `POST /api/admin/campagnes/{c}/classement` est **idempotent** tant qu'aucune `publication` n'existe (409 sinon) : il upsert `rang`/`decision`, supprime les décisions devenues non classables, **préserve** `motif_interne`/`motif_communicable` (gérés par `PUT .../decision/motifs`, admin strict).
- **D-5a-3** : `TAILLE_LISTE_ATTENTE = 8` est une constante de `ServiceClassement` (comme `moisApprox`/`pointsParEtoile`). **Point ouvert** : contrairement aux constantes de calcul, c'est un paramètre métier qui pourrait devenir un attribut de `campagne_filiere` si un ajustement par campagne se confirme.
- **D-5a-4** : un candidat **`non_eligible`** dont le dossier ET l'entretien sont validés reçoit une décision **explicite** `non_retenu` + `motif_interne = 'non éligible'` (🔴, système), `rang = NULL` (migration : `decision_candidature.rang` rendu nullable). Écart assumé à la maquette (qui l'exclut du classement sans ligne) pour que **tout** candidat ait un résultat déterminé au Lot 5b. Règle reine préservée : après publication, ce candidat verra **exactement** le même message qu'un non-retenu ordinaire — il n'apprend jamais que la cause était l'inéligibilité (`motif_interne` reste 🔴). Non-éligible ≠ non-retenu en interne, convergents vers le même message candidat.
- Rôles : `POST` classement + `GET` classement + `PUT` motifs = **administrateur strict** (le classement global expose les scores/rangs de tous les candidats, toutes filières ; un évaluateur n'a de légitimité que sur ses affectations — cf. classement.html côté admin). Un besoin borné « évaluateur voit sa filière » serait ajouté précisément si nécessaire.

## ADR-10 — Rôles : `utilisateur` + spécialisation `candidat` / `membre_equipe`, admin ⊇ évaluateur

**Contexte.** Champs très différents entre candidat (état civil, réponses formulaire...) et équipe projet (poste...) ; comportement observé dans la maquette où un compte admin peut effectuer toutes les actions évaluateur, plus les siennes propres.
**Décision.** `utilisateur` porte l'identité + le rôle ; `candidat` et `membre_equipe` sont deux sous-types exclusifs (CIF, cf. `docs/mcd.md`). Les policies Laravel autorisent `evaluateur` ET `administrateur` sur les endpoints d'évaluation/entretien ; `correction exceptionnelle` et les endpoints d'administration restent strictement réservés à `administrateur`.
**Conséquence.** Pas de duplication de logique de permission entre "évaluateur" et "administrateur agissant comme évaluateur" — une seule policy par action, avec un rôle autorisé à plusieurs valeurs quand c'est le cas.

**Portée d'accès (Lot 4a).** Sur l'espace évaluateur : un **évaluateur** n'accède qu'aux candidatures où `candidature.evaluateur_id = son membre_equipe.id` (ses affectations) ; un **administrateur** accède à **toutes** les candidatures instructibles (admin ⊇ évaluateur, conforme à `candidatures.html` admin de la maquette). Un dossier affecté à un autre évaluateur → **404** (`Response::denyAsNotFound`, cohérence zéro-fuite avec l'isolation candidat). Les Resources évaluateur (`App\Http\Resources\Evaluateur\*`) sont **distinctes** des Resources candidat et jamais réutilisées en croisé : l'évaluateur voit la zone 🔴 du dossier qu'il instruit (`statut_interne`, `statut_eligibilite_interne`, `verification_dossier`, critères éliminatoires), le candidat n'en voit **rien** (garanti par `StatutPublicResolver` + liste blanche `CandidatureCandidatResource`, testé sur le vrai chemin).

## ADR-11 — Pièces justificatives stockées hors webroot

**Contexte.** Documents personnels (CNI, diplôme...) — ne doivent jamais être accessibles par une URL publique directe.
**Décision.** `piece_justificative.chemin_stockage` pointe vers un espace de stockage Laravel non exposé par nginx (`storage/app/private/documents`, disque `documents`, volume Docker dédié `documents_data`, cf. `docker-compose.yml`). Tout accès passe par une route applicative authentifiée et autorisée (policy : le candidat propriétaire, ou un membre équipe affecté/admin), jamais par un lien statique.
**Conséquence.** Un peu de latence supplémentaire (le fichier transite par PHP au lieu d'être servi directement par nginx) en échange d'un contrôle d'accès réel et audité.

**Durcissement (Lot 3b).**
- Le disque Laravel `local` (`storage/app/private`) est passé en `'serve' => false` : la route `GET|PUT /storage/{path}` que Laravel enregistre sinon (accès/upload par URL signée) **n'existe plus** (`php artisan route:list` ne montre aucune route `storage`). Le disque dédié `documents` a lui aussi `serve => false`.
- Le **nom de stockage est 100 % serveur** (`{candidature_id}/{uuid}.{ext}`, `ext` dérivée du MIME détecté par contenu) — jamais construit à partir du nom ou de l'extension client (pas de path traversal, pas de collision). `nom_original` est conservé assaini, pour l'affichage seul.
- Validation d'upload : `mimetypes` (MIME réel détecté par `finfo`, pas le `Content-Type` déclaré) + `extensions` (garde-fou) + `max` 10 Mo. Formats : PDF, JPEG, PNG.
- Téléchargement en **streaming** depuis le disque privé (`Storage::download`), toujours `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` (jamais `inline` : un PDF/image valide peut porter une charge active).
- `piece_justificative.type_mime` (colonne ajoutée au Lot 3b, cf. `docs/mld.md`) mémorise le MIME détecté pour servir le bon `Content-Type` sans re-scan.

## ADR-12 — Journal d'audit immuable : application **et** garantie PostgreSQL

**Contexte.** Règle 5 : traçabilité persistante des actions sensibles. L'append-only strictement applicatif (absence de route de modification) protège contre le code métier normal, mais pas contre un accès direct à la base ni contre une future route mal écrite.
**Décision.** `journal_audit` est append-only, garanti à **deux niveaux** :
1. **Applicatif** — aucune route, policy ou contrôleur ne propose de mise à jour ou de suppression sur ce modèle. Chaque action sensible (correction exceptionnelle, remplacement, publication, modification de grille, activation/désactivation de filière, ouverture/clôture de campagne, affectation, élimination manuelle, motif de non-retenue) écrit une ligne, avec motif obligatoire quand la règle métier l'exige.
2. **PostgreSQL (tranché au Lot 1)** — une migration dédiée (`..._add_journal_audit_append_only_trigger`) installe une fonction PL/pgSQL et deux triggers sur `journal_audit` : `BEFORE UPDATE OR DELETE` (par ligne) et `BEFORE TRUNCATE` (par instruction). Toute tentative lève `RAISE EXCEPTION` (`ERRCODE restrict_violation`) et est rejetée. Seul `INSERT` reste permis.

*Trigger plutôt que `REVOKE UPDATE, DELETE`* : le trigger protège indépendamment du rôle SQL utilisé, y compris le propriétaire des tables dont se sert Laravel (qu'un `REVOKE` sur le rôle applicatif n'atteindrait pas).

**Conséquence.** L'immuabilité ne repose plus sur la seule absence de chemin applicatif : un `UPDATE`/`DELETE`/`TRUNCATE` sur `journal_audit` échoue au niveau moteur, quel que soit le point d'entrée (route, `php artisan tinker`, `psql` direct, script de maintenance). Le `DROP TABLE` de `migrate:fresh` n'est pas concerné (DDL de gestion de schéma, pas une altération de ligne) ; un contournement resterait théoriquement possible pour un super-utilisateur PostgreSQL via `SET session_replication_role = replica`, ce qui n'est pas le rôle applicatif et sortirait de tout usage normal. Corollaire opérationnel : une ligne insérée par erreur ne peut pas être « nettoyée » — les tests du trigger s'exécutent donc en transaction annulée (`ROLLBACK`).

## ADR-13 — Pas de parcours d'inscription dédié : la création de candidature le porte temporairement (Lot 3a) — **RÉSOLU au Lot 7 (ADR-16)**

**Contexte.** Dans la maquette, `inscription.html` crée le couple `candidat` + `candidature` : il fixe la filière visée (`filiere_id`), génère le `numero_dossier`, initialise le classement des préférences et met `statut='brouillon'`. Aucun lot livré (0 à 3a) n'a produit d'endpoint d'inscription ; le Lot 2 se limite à l'authentification et à 3 comptes de démonstration seedés (le `candidat` de démo est créé par un seeder).
**Décision.** Au Lot 3a, `POST /api/candidatures` **porte le geste d'inscription** : il prend `filiere_id` en entrée (filière ouverte pour la campagne en cours), génère le `numero_dossier` (`CASA-<année>-<6 chiffres>`), crée la ligne `reponse_formulaire` vide (1-1 strict) et pré-remplit `classement_filiere_preference` (filière visée en rang 1). L'édition des champs d'identité du `candidat` (`prenom`, `nom`, `date_naissance`, `cni`…) **n'est pas** couverte par ce lot.
**Conséquence — LEVÉE au Lot 7 (ADR-16).** `POST /api/register` crée désormais le compte (`utilisateur` role=candidat + `candidat`) ; `POST /api/candidatures` est **inchangé** (il lisait déjà `user()->candidat`, il ne créait jamais le `candidat`) et **garde `filiere_id`** — la suggestion « filière du profil » d'origine est écartée : la filière est un choix **par candidature** (re-candidature possible sur une autre filière à une cohorte ultérieure), et `classement_filiere_preference` est déjà porté par la candidature (**D-7-1**). L'édition d'identité passe par `PATCH /api/candidat/profil`.

**Dépendance signalée (D-4a-1) — RÉSOLUE au Lot 6a.** Le Lot 4a consommait `candidature.evaluateur_id` en lecture sans endpoint pour l'écrire (contexte posé par le trait `CreeContexteEvaluation` / le seeder `DemoEvaluationSeeder`). Le Lot 6a fournit **`POST /api/admin/affectations`** (`role:administrateur` strict) : affectation **en masse** (`{ evaluateur_id, candidature_ids: [1..n] }`), cible = `membre_equipe` de rôle `evaluateur`, candidatures affectables `statut_interne ∈ {soumis, en_instruction}` (**atomique** : 422 + liste si une seule ne l'est pas), `soumis → en_instruction` (la convention « en instruction dès l'affectation » devient un comportement testé sur le vrai chemin), ré-affectation possible tant que `en_instruction`. Le trait/seeder restent comme raccourci rapide.

## ADR-14 — Espace administration : gestion & supervision (Lot 6a)

**Contexte.** Après le cœur métier (candidature → évaluation → classement → publication), l'admin a besoin d'outils de gestion (affectation, filières, campagnes) et de supervision (audit).
**Décision.** Tous les endpoints sous `role:administrateur` strict (ADR-10), namespace `App\Http\Controllers\Api\Admin\*`. La **correction exceptionnelle**, le **remplacement** (indisponible → promotion) et l'**élimination manuelle** — actes qui cassent un invariant — sont explicitement **hors périmètre 6a** (Lot 6b).
**Conséquence.**
- **Filières** (`PATCH /api/admin/filieres/{filiere}` `{actif}`) : une filière `actif = false` fait échouer `POST /api/candidatures` (Lot 3a) en **422** (« Cette filière n'accepte pas de candidature actuellement »). Idempotent (pas d'audit si inchangé).
- **Campagnes** (`PATCH /api/admin/campagnes/{campagne}` `{statut}`) : transitions `brouillon → ouverte` (409 si une autre campagne est déjà ouverte — règle « une seule ouverte » du 3a) et `ouverte → cloturee` uniquement ; toute autre → **422**. Après clôture, `POST /api/candidatures` répond **409** (« Aucune campagne ouverte », déjà en place). La **création** de campagne (dates, places) est reportée (**D-6a-2**).
- **Audit** (`GET /api/admin/audit`) : lecture seule (immuabilité déjà garantie par le trigger PostgreSQL + l'absence de route, ADR-12). Filtres `module` / `action` / `auteur` (email) / `date_debut` / `date_fin` / `recherche`. **`recherche` est borné à `action` + `objet`** — jamais `ancienne_valeur` / `nouvelle_valeur` / `motif` (🔴 : scores, motifs internes) : une recherche plein-texte sur ces colonnes serait un moyen détourné de fouiller le contenu confidentiel en masse. `AuditResource` (🔴) n'est utilisée que par `AuditController` ; aucun autre rôle ne lit `journal_audit` (les autres n'y font qu'écrire).
- **Supervision** (`GET /api/admin/candidatures`) : vue transverse (`CandidatureAdminResource`, 🔴 admin-only, distincte des Resources candidat/évaluateur), filtres statut / filière / évaluateur (`non_affecte`) / campagne ; brouillons exclus par défaut.
- **Route publique** (`GET /api/filieres`, hors `auth:sanctum`) : **première route publique du projet**. `FiliereResource` = liste blanche stricte de **4 champs 🟢** (`code`, `nom`, `description`, `actif`) — ni `id`, ni `quota`, ni rien du modèle interne. Une filière désactivée reste listée (`actif: false`).
- **D-6a-1** : l'affectation écrit **1 ligne `journal_audit` par candidature** (`action = "Affectation évaluateur"`), là où `candidatures.html` fait 1 ligne globale « N dossiers » — divergence dans le bon sens (audit exploitable en cas de litige).
- **D-6a-3** : l'élimination manuelle (`candidatures.html` : admin force `non_eligible` + motif) est reportée au Lot 6b (acte cassant un invariant).
- **D-6a-4** (correctif transverse) : `GET /api/candidature` (`courante`, Lot 3a) ne filtre plus sur `campagne.statut = 'ouverte'` — il renvoie la candidature la plus récente du candidat. Sinon, dès qu'un admin clôture la campagne (nouveau au 6a), le candidat perdrait l'accès à son propre dossier **et à sa décision publiée** (Lot 5b : la publication suit typiquement la clôture). Seule la CRÉATION (`store`) exige toujours une campagne ouverte.

**~~Point ouvert à porter au lot inscription (D-3c-1)~~ — RÉSOLU au Lot 7.** Le contrôle d'éligibilité `residence_ci` (résider en Côte d'Ivoire) n'est présent dans `scoring.js` que dans `checkEligibiliteInitiale` (§4.2, inscription), **pas** dans `checkCriteresEliminatoires` (§4.9, soumission). Le Lot 3c portait fidèlement `checkCriteresEliminatoires`. Le Lot 7 porte `checkEligibiliteInitiale` **là où scoring.js le place** — à l'inscription : `ServiceEligibiliteInitiale` (`VERSION=1`) refuse `POST /api/register` en 422 si l'âge n'est pas dans [18,30] (référence = maintenant) ou si `residence_ci = false`. `ServiceEligibilite::evaluerSoumission` **reste inchangé** (pas de `residence_ci` à la soumission). La dette est donc close au bon endroit : aucun compte candidat ne peut exister hors tranche d'âge ou hors CI (**D-7-3**).

## ADR-15 — Actes exceptionnels tracés : correction, remplacement, élimination manuelle (Lot 6b)

**Contexte.** Trois gestes d'administration cassent un invariant du cœur métier : rouvrir une évaluation verrouillée (ADR-04), rétrograder/promouvoir une décision publiée (règle reine / ADR-08), forcer une inéligibilité hors `ServiceEligibilite` (ADR-06). Ils sont indispensables (erreur de saisie, désistement d'un lauréat, fraude découverte) mais doivent rester rares, tracés et réservés à `administrateur` strict (ADR-10).
**Décision.** Trois endpoints sous `role:administrateur` / `App\Http\Controllers\Api\Admin\*`, **`motif` obligatoire** (422 sinon), **1 ligne `journal_audit` par acte** portant l'intégralité du changement `ancienne_valeur → nouvelle_valeur` (D-6b : reconstituable à la seule lecture de la ligne).
- **Correction exceptionnelle** (`POST /api/admin/candidatures/{c}/correction/dossier` | `/entretien`) — **seule exception au verrouillage ADR-04**. Surface large (D-6b-1) : réponses candidat + vérification + notation. Le nouveau snapshot **écrase** l'ancien (MLD 1-1) ; l'historique vit dans l'audit. Recalcul 100 % serveur sur la **grille active** (D-6b-1), puis **relance complète de `ServiceEligibilite`** (les entrées ont changé) → `statut_eligibilite_interne` + retrace `critere_eliminatoire_declenche` ; `statut_interne` reste `evalue`. **Pré-publication uniquement** (D-6b-2) : **409** si la campagne est publiée — corriger une décision communiquée relève du contentieux, pas du logiciel. Re-corrigible (un nouvel acte tracé, jamais un undo).
- **Remplacement** (`POST /api/admin/remplacements` `{candidature_id, motif}`) — acte **post-publication** (422 si non publiée : avant, relancer le classement). Précondition : `decision = 'retenu'` (422 sinon). Promeut le **premier `liste_attente` de la même filière par `rang`** ; sortant → `indisponible`, promu → `retenu` (rangs inchangés). Ligne `remplacement` + audit. Liste d'attente vide → acte tracé **sans promu**. `StatutPublicResolver` gère la transition **sans logique spéciale** (il lit `decision` en direct). `indisponible` est un statut **factuel neutre** (D-6b : Q5) — il ne révèle rien d'interne, distinct du `non_eligible` qu'on masque en `non_retenu` générique. **Non-fuite** (D-3b-7) : ni score, ni rang, ni le fait même du remplacement ne transparaît côté candidat. Irréversible.
- **Élimination manuelle** (`POST /api/admin/candidatures/{c}/elimination` `{motif}`) — force `statut_eligibilite_interne = 'non_eligible'` + 1 ligne `critere_eliminatoire_declenche` d'**`origine = 'decision_administrative'`** (D-6b-3 : valeur ajoutée au CHECK, migration `2026_09_08_100000` — on ne réutilise pas `verification_evaluateur`, ça mentirait sur l'origine). `statut_interne` inchangé (verdict ≠ position workflow — divergence assumée avec `candidatures.html`). Décision existante → `non_retenu` générique (`motif_communicable` préservé) : après publication, **indiscernable** d'un non-retenu ordinaire (règle reine, D-5b-1). **Pas** de promotion automatique (D-6b : Q7 — fraude ≠ désistement). Une par une (D-6b-4). Irréversible.

**Conséquence.** Aucune colonne de « correction » sur `candidature` (D-6b : Q9) : la trace vit exclusivement dans `journal_audit`. `effectue_par` / `valide_par` = `membre_equipe` de l'admin (422 si profil équipe incomplet, D-6b : Q8).

## ADR-16 — Inscription & profil candidat : la porte d'entrée (Lot 7, comble ADR-13)

**Contexte.** Jusqu'au Lot 6b, les comptes candidats venaient de seeders et `POST /api/candidatures` « portait » le geste d'inscription (ADR-13). Il manquait la création de compte self-service et la gestion de l'état civil.
**Décision.** Frontière nette en trois gestes :
| Geste | Endpoint | Effet |
|---|---|---|
| **Inscription** | `POST /api/register` (**public**, `throttle:register` = 3/min + 20/jour par IP) | crée `utilisateur` (role=`candidat`) + `candidat`, **rien d'autre** ; transaction unique ; **auto-login** (session régénérée) ; `journal_audit` « Inscription candidat » |
| **Profil** | `GET` + `PATCH /api/candidat/profil` (`role:candidat`, **sans paramètre d'URL**) | lecture / édition de son état civil ; `journal_audit` « Mise à jour du profil » |
| **Candidature** | `POST /api/candidatures` (**Lot 3a, code inchangé**) | crée la candidature pour un candidat déjà inscrit |

- **Éligibilité initiale** (`App\Domain\Eligibilite\ServiceEligibiliteInitiale`, `VERSION=1`, portage fidèle de `scoring.js checkEligibiliteInitiale`) : `POST /api/register` **refuse en 422** (motif explicite) si âge ∉ [18,30] (référence = maintenant) ou `residence_ci = false`. **`evaluerSoumission` inchangé** → double gate assumé (âge re-contrôlé à `campagne.date_ouverture`). Ferme **D-3c-1**.
- **`residence_ci`** : fixé et contrôlé **à l'inscription uniquement** — **non éditable** via le profil (`prohibited` → 422). Un vrai changement de résidence relève d'une démarche administrative, pas d'un toggle self-service.
- **Sécurité** : e-mail `unique` ; mot de passe `Password::min(10)->letters()->numbers()->mixedCase()` (pas de symbole imposé — NIST privilégie la longueur ; pas de contrôle HaveIBeenPwned en v1 — **durcissement futur**) ; hash bcrypt 12 rounds (cast `hashed`). **E-mail déjà pris → message explicite** (« Un compte existe déjà pour cette adresse e-mail. ») : l'inscription diffère légitimement du login (l'utilisateur a besoin de savoir qu'il a déjà un compte) ; l'abus est borné par le throttle.
- **CGU** : `required|accepted` **et horodatées** (`utilisateur.cgu_acceptees_le`, migration `2026_09_09_100000`) — l'acceptation est un acte juridique, prouver *quand* elle a eu lieu a de la valeur en litige (cohérent ADR-12).
- **ADR-07** : `nationalite` / `diplome` / `diplome_verifie` / `sc04*` sont `prohibited` sur `/register` **et** sur `/profil` — jamais déclarés par le candidat.
- **Resource** : `CandidatResource` (déjà la liste blanche stricte des 8 champs 🟢) réutilisée — aucune nouvelle Resource.

**Divergences maquette.**
- **D-7-1** : inscription et candidature **séparées** (le wizard `inscription.html` fusionne compte + filière + candidature). `filiere_id` reste sur `POST /api/candidatures`.
- **D-7-2** : `email` éditable dans `candidature.html` étape 1 → **exclu** de `PATCH /api/candidat/profil` (changement de *credential* → flux dédié avec ré-authentification — **point ouvert**).
- **D-7-3** : `residence_ci` contrôlé à l'inscription (ferme D-3c-1), non ajouté aux critères de soumission.
- Vérification d'e-mail par code (wizard étape 3, **simulée** dans la maquette : code « 2026 » pré-rempli) → **hors périmètre**, point ouvert (aucun envoi d'e-mail réel dans le projet).
- Format téléphone : la maquette impose `225` + 10 chiffres ; le backend reste **souple** (`string, max:20`) pour ne pas fragiliser sur les plans de numérotation ni toucher aux données de démo.

## ADR-17 — Frontend : fondation React (Lot 8a)

**Contexte.** Après un backend complet (Lots 0-7), on démarre le frontend qui consomme l'API. Le Lot 8a pose le **socle** — aucun écran métier, mais l'ossature (CSS, client HTTP, auth, routing) sur laquelle s'appuieront les espaces (8b/c/d).
**Décision.**
- **Design** : le CSS de la maquette (`App_maquette/assets/css/`, validé par la direction) est **copié verbatim** dans `frontend/src/styles/` (le contexte de build Docker ne voit que `frontend/`) et importé **globalement** (pas de CSS Modules — les classes `btn`, `card`, `sidebar-link`… sont globales par nature). En-tête de `src/styles/index.css` : avertissement « copie, ne pas éditer ici ». **Le template Vite par défaut est supprimé** (`App.css`, `index.css` violet, `src/assets/`, `public/icons.svg`) — son `#root { max-width:1280px; text-align:center }` cassait l'app-shell pleine largeur (**piège de spécificité résolu**).
- **Polices & icônes empaquetées** (D-8a-3) : `@fontsource/inter`, `@fontsource/plus-jakarta-sans`, `@fortawesome/fontawesome-free` en dépendances npm au lieu des `<link>` CDN de la maquette — **rendu identique**, mais pas de dépendance à un tiers au runtime (robustesse hors-ligne / CI).
- **Client HTTP unique** (`src/lib/apiClient.js`, ADR-01/02) : base `VITE_API_URL` (défaut `/api`), `credentials: 'include'`, **cycle CSRF** (`GET /sanctum/csrf-cookie` mémoïsé avant toute mutation, `X-XSRF-TOKEN` depuis le cookie décodé), **retry unique sur 419**, erreurs normalisées en `ApiError` typée (`unauthenticated` / `forbidden` / `validation` / `csrf` / `rate_limited` / `server` / `network`). **Aucun jeton stocké côté JS** — ni `localStorage`, ni `sessionStorage` ; seuls les cookies (session `httpOnly` + `XSRF-TOKEN`) portent l'auth.
- **Contexte d'auth** (`src/auth/`) : `status` ∈ `loading` / `authenticated` / `guest`. Au boot **et à chaque rechargement de page**, l'état est reconstruit **exclusivement depuis `GET /api/me`** (le cookie de session, lui, persiste). `login()` utilise directement le `UserResource` renvoyé par `POST /api/login` (pas de `/me` supplémentaire).
- **Routing protégé par rôle** (`react-router-dom` v7) : `ProtectedRoute` — `loading` → écran de chargement ; `guest` → `/connexion` (mémorise l'URL) ; **mauvais rôle → redirigé vers SON espace** (`roleHome`), pas une page 403. Gardiennage **strict par rôle principal** en 8a.
  **⚠️ À REBRANCHER AU LOT 8c** : ADR-10 (« administrateur ⊇ évaluateur ») est une règle API ; côté navigation, l'accès admin aux écrans d'évaluation devra être rouvert quand ces écrans arrivent.
- **Fallback SPA** (D-8a-1) : le conteneur `frontend` gagne un `nginx.conf` (`try_files $uri /index.html`) — l'image nginx par défaut renvoie 404 sur toute route client. `docker/nginx/default.conf` (proxy externe) **inchangé**. **Backend strictement inchangé.**
**Conséquence.** Écran de connexion réel + placeholders par espace. Preuve (Lot 8a) : `build` + `lint` + `vitest` (20 tests) verts ; smoke `curl` Docker — `/` et `/connexion` → 200 (fallback), cycle Sanctum des 3 comptes démo (csrf → login → `/api/me` bon rôle → **2ᵉ `/api/me` = reload → toujours authentifié** → logout → 401). E2E navigateur repoussé au 8b (le wizard le justifiera).

## ADR-18 — Frontend : espace public + inscription (Lot 8b-1)

**Contexte.** Après la fondation (8a), on construit la porte d'entrée visible : accueil public (présentation, procédure, critères d'élimination, filières) + inscription self-service, avant le formulaire de candidature (8b-2).
**Décision.**
- **Accueil** (`HomePage`, route `/` pour les visiteurs) : contenu éditorial **repris de `App_maquette/index.html`**. Filières via `GET /api/filieres` (public) — `actif:false` → « Actuellement fermé », candidature indisponible (§16). Icône de filière : table client `code → FA` (l'API ne l'expose pas, **D-8b1-3**) ; pas de modale « détail » (ni `competences` ni `quota` servis).
- **CONFIDENTIALITÉ DE LA VITRINE (§12-13)** — point central. La page informe sur les **critères d'élimination** (âge, disponibilité, résidence, niveau de français, sites, diplôme > CEPE, nationalité… — 11 items dérivés de `checkCriteresEliminatoires`) mais **ne révèle jamais la grille de notation** : le contenu éditorial est **scrubbé** de tout barème.
  - « Classement par filière — **~~Score final sur 100~~**, départage par critères de priorité » → « En cas d'égalité de score, des critères de priorité s'appliquent ». Le « /100 » était le **seul** nombre de barème de la maquette.
  - « Grille de notation **~~pondérée~~** » → « Grille de notation **interne**, appliquée par l'équipe d'évaluation ».
  - FAQ « comment est évalué mon dossier ? » : le message « **le détail de cette grille est un document interne, réservé à l'équipe d'évaluation** » est **conservé** — il renforce la légitimité de la sélection.
  - FAQ « égalité de score » : la politique d'équité (priorité mixité / vulnérabilité / expérience secteur / motivation) est **conservée dans le fond** mais **reformulée sans mécanique numérotée** (« critère 1 puis 2 » → phrase de politique).
  - Test Vitest **et** smoke Docker : le HTML/bundle de l'accueil ne contient ni `/100`, ni `sur 100`, ni `/65`, ni `/35`, ni `pondération`, ni `sous-critère`.
  - **⚠️ POINT OUVERT INSTITUTIONNEL** : la formulation finale des FAQ « évaluation » et « égalité de score » relève d'une **décision de communication publique** — à faire **relire par les partenaires (CCI-CI / FADV / AICS) avant mise en production**, pas seulement par l'équipe technique.
- **Inscription** (`InscriptionPage`, route `/inscription`) : **étape 1 seule** du wizard maquette (état civil + identifiants + CGU), → `POST /api/register` via `AuthContext.register()` → auto-login → `/candidat`. Erreurs : 422 avec `errors` → **champ par champ** ; 422 `message` seul (âge/résidence, `abort(422,…)` du Lot 7) → alerte globale ; e-mail déjà pris → sous le champ ; 429 → message dédié. **D-8b1-1** : case obligatoire « Je déclare résider en Côte d'Ivoire » (la maquette force `true` sans UI). Choix de filière → 8b-2 ; vérification e-mail → hors périmètre (ADR-16).
- **Shell + dashboard candidat** : `AppShell` (8a) + `CandidatDashboard` **minimal** — consomme `GET /api/candidature` (404 → état « compte créé, dossier à venir » ; 200 → statut public + n° dossier). Nav latérale : seul « Tableau de bord » navigable ; le reste arrive aux sous-lots suivants.
- **E2E Playwright** : installé ici (chromium ; le projet « mobile » utilise une **largeur** de 390 px sans `isMobile` — les captures `fullPage` sous émulation mobile Playwright produisent des hauteurs erronées). `frontend/playwright.config.js` — joue contre la **stack Docker** (`:8080`), pas de `webServer`, timeouts **généreux** (latence Docker-Windows ~4-5 s/requête). Parcours `e2e/parcours-inscription.spec.js` : accueil → inscription (e-mail horodaté unique) → dashboard → **rechargement → session conservée**. Captures `e2e/captures.spec.js` (accueil / inscription / connexion en desktop 1280 + largeur mobile). **Base E2E** : la suite crée un vrai compte par run dans `casa` (dev) — `migrate:fresh --seed` réinitialise ; ne cible pas la base des smokes d'autres lots.
- **D-8b1-2 (correctif CSS SPA)** : `reset.css` (vendored, maquette) pose `html, body { height: 100% }` — pensé pour des pages HTML distinctes. Dans la SPA, tout l'arbre vit dans `#root` : `html`/`body` restaient plafonnés à la hauteur du viewport, `document.documentElement.scrollHeight` était tronqué (captures pleine page / impression coupées). Correctif dans `src/styles/index.css` (fichier applicatif, **pas** la copie vendored) : `html, body { height: auto; min-height: 100dvh }` + `#root { min-height: 100dvh }`. Aucun impact visuel.

**Conséquence.** Backend **strictement inchangé**. Preuve : `vitest` (35 tests, dont la non-fuite grille sur le HTML de l'accueil), E2E Playwright vert + captures, smoke `curl` (HTML public sans terme de barème, `register` réel → 201 → `/api/me` = candidat, `/inscription` → 200 fallback SPA).

## ADR-19 — Frontend : formulaire de candidature (wizard 10 étapes, Lot 8b-2)

**Contexte.** Écran candidat central : le dossier complet, majoritairement rempli au smartphone. Consomme l'API d'édition des Lots 3a/3b/3c. Deux exigences dominent : (1) **confidentialité** — le bundle est public, il ne doit jamais laisser fuir un point de barème (rappel ADR-02) ; (2) **responsive** — cibles ≥ 44 px, pas de scroll horizontal à 360 px.

**Décision.**
- **Structure du formulaire = constante frontend** (`wizard/formStructure.js`, **D-8b2-3**). Le backend ne sert pas la grille à un candidat (pas de `GET /api/grille`) : les libellés des questions/options sont une **transcription MANUELLE et vérifiée** de `App_maquette/assets/js/scoring.js` (`CASA_GRILLE`), **dépouillée** de tout `points` / `max` / `poids` / `pointsParEtoile` / `notationEvaluateur`. Aucun `/65`, `/35`, `sur 100`, `pondération` nulle part. **SC.04 (plus haut diplôme), MO.04 note en étoiles, nationalité** sont volontairement **absents** — le candidat ne les saisit jamais, le backend les refuse déjà.
  - Test **Vitest** (`formStructure.test.js`) : `JSON.stringify` de tout le module + marche récursive des clés → zéro terme/clé de barème ; `\bpts?\b` / `\bpoints?\b` faux.
  - Test **smoke** : grep du **bundle JS entier** (`sur 100`, `/65`, `/35`, `pointsParEtoile`, `pondération`, `sous-critère`, `barème`, `\bpoints\b`, `N pts`). ⚠️ `\bpt\b` seul percute des identifiants minifiés de React/React-Router (`function pt(){…}`) — on cible donc le point comme **unité** (adjacent à un chiffre) + les termes de grille. Fuite corrigée au passage : `HomePage.jsx` disait « Ces **points** sont contrôlés… » (sens : « ces critères ») → reformulé.
- **Après soumission, le candidat ne voit rien de son éligibilité.** `POST /soumettre` répond neutre (`numero_dossier` + `statut_public`), le wizard bascule en écran « déjà soumis » (non éditable), les `PATCH` renvoient 409. Le récap n'affiche aucun score (« Diplôme : vérifié par l'équipe d'évaluation »).
- **Persistance HYBRIDE** (**D-8b2-4**) : réponses `reponse_formulaire` → `PATCH .../reponses` **en lot** (champs modifiés uniquement) au « Suivant » / « Brouillon » ; expériences, pièces, justificatifs → **immédiats** (IDs serveur, stockage hors-webroot) ; classement → `PUT .../classement` au **départ de l'étape 7** (pas à chaque flèche). La candidature est **créée à l'étape 2** (`POST /api/candidatures {filiere_id}`), pas à l'inscription.
- **« Suivant » attend la confirmation du serveur.** Sur connexion lente, l'étape n'avance **pas** tant que le `PATCH` n'a pas répondu ; échec → l'utilisateur reste sur l'étape avec une alerte, le brouillon n'est jamais « perdu en silence ». Contrôle de complétude **client léger** (`completeness.js`, miroir de `ValidateurCompletude`) — bloque une étape manifestement incomplète et signale les champs, mais **l'autorité reste le 422 de `POST /soumettre`**. Navigation arrière/récap **libre**.
- **422 de complétude à la soumission** : le récap liste les manques (`submitErrorLabel`) avec un bouton **« Corriger »** qui saute à l'étape concernée (`submitErrorStep` : `reponses.sc0*` → scolaire, `experiences.N.*` → expérience, `pieces_dossier` → documents, etc.).
- **Filière choisie DANS le wizard** (**D-8b2-1**) : l'inscription (8b-1) ne la collecte pas (D-7-1). Étape 2 = choix (cartes) → case de confirmation → `POST .../confirmer-filiere` (irréversible). La confirmation n'est envoyée qu'au « Suivant » : la porte de l'étape se gate donc sur l'**état local** (choix + case cochée), pas sur `candidature.cqp_confirme` qui n'est vrai qu'**après** commit.
- **Identité (étape 1)** limitée aux champs du **profil** (`PATCH /api/candidat/profil`, Lot 7), **e-mail en lecture seule** (flux dédié, D-7-2), **`residence_ci` absent** (fixé à l'inscription, Q2b Lot 7), ville en champ libre (**D-8b2-2**).
- **`FiliereResource` : ajout de `id`** (**D-8b2-5**, révision assumée). `GET /api/filieres` exposait `{code, nom, description, actif}` ; le frontend candidat a besoin de l'UUID pour `POST /api/candidatures {filiere_id}` et `PUT .../classement`. **Ce n'est ni un score, ni un rang, ni un quota** — et il est déjà exposé au candidat authentifié via `GET /api/candidature`. **L'identifiant de filière est public.** `FilieresPubliquesTest` ajusté : liste blanche `['id','code','nom','description','actif']`, `id` chaîne, toujours **jamais** `quota` / `icone` / `campagne` / timestamps.
- **Composants responsive** (`components/form/`) : Oui/Non en **segmenté** (`.radio-segmented`, `<input type=radio>` réel), 3-7 options longues en **cartes empilées** (`RadioCardList`), échelle langues `NiveauScale` (`.segmented` → **grille 2×2 sous 420 px** via `CandidatureWizard.css`), `RankList` (glisser-déposer HTML5 **+ flèches ↑/↓ ≥ 44 px** — seul mécanisme déclenchable au toucher), `FileDropRow` (garde-fous type/taille client avant upload, erreur 422 serveur sous la ligne), `WizardFooter` (**empilé mobile, action principale en haut** via `order`). Correctifs a11y au passage : `SegmentedRadio` / `RadioCardList` — `role="radiogroup"` désormais réellement nommé (`<legend id>` + `aria-labelledby`) ; selects « Domaine » / « Durée » des expériences associés à leur `<label>` (`htmlFor`).
- **`window.scrollTo`** stubé dans `src/test/setup.js` (jsdom ne l'implémente pas, le wizard le rappelle à chaque « Suivant »).

**Conséquence.** Backend : **une seule** évolution (`FiliereResource` + son test). Preuve : `vitest` **71 tests** (8 wizard d'intégration — « Suivant » attend le PATCH, échec ⇒ pas d'avancée, création filière étape 2, matérialisation d'une expérience, 422 complétude → boutons « Corriger » ; 7 `formStructure` non-fuite ; 21 `completeness`), `php artisan test` **296**, E2E Playwright `parcours-candidature.spec.js` (inscription → 10 étapes → upload PDF/PNG réels → classement → soumission → **modale** → écran « déjà soumis » ; **brouillon fiable** après reload ; **`PUT classement` capté au « Suivant » de l'étape 7**), captures `captures-candidature.spec.js` à **360 / 390 / 768 px**, smoke `smoke8b2.sh` (bundle sans barème + parcours `curl` complet : `register` → candidature → `confirmer-filiere` → `reponses` → expérience+justificatif → `classement` → 6 pièces → `soumettre` **200 neutre** → re-`soumettre` **409** → `PATCH` post-soumission **409** ; 422 champ-par-champ ; 422 complétude avec familles de clés).

**Divergences maquette.** Pièces : la maquette dit « PDF, JPEG » — le backend accepte **PDF / JPEG / PNG** (`ContraintesFichier`), libellé aligné sur le backend.

## ADR-20 — Frontend : suivi & résultat candidat (Lot 8b-3)

**Contexte.** On termine l'espace candidat : le **suivi** de la candidature puis, après publication, l'**affichage du résultat**. C'est l'écran où la **règle reine** (règle non négociable 1, contexte §14-17) se joue côté UI — `ma-candidature.html` de la maquette la **viole** doublement (bannière « Candidature non éligible » l.78-79, et un timeline granulaire l.50-72 qui expose chaque jalon interne).

**Décision.**
- **Un seul écran `MaCandidature`** (`/candidat/ma-candidature`) + **dashboard** complété, tous deux alimentés par le hook `useMaCandidature()` qui consomme `GET /api/candidature` et **n'expose que 9 primitives d'affichage** (`statutPublic`, `decision`, `motifCommunicable`, `numeroDossier`, `dateSoumission`, `filiereNom`, `campagneNom`, `piecesCount`, `status`), **copiées telles quelles** — aucune dérivation. `reponses` / `experiences` / `classement` (pourtant dans le payload) ne sont **pas** remontés. `StatutPublicResolver` a déjà tout fait côté serveur (ADR-03).
- **Rendu conditionnel par `statut_public` SEUL** :
  - `brouillon` (ou 404) → empty-state + CTA vers le wizard ;
  - `en_cours_de_traitement` → **une** phrase neutre (« Votre dossier suit son cours. Le résultat vous sera communiqué à l'issue du processus de sélection. »), rien d'autre — pas d'« un évaluateur regarde votre dossier » ;
  - `decision_publiee` → bannière **résultat** par `decision` : `retenu` (félicitations + filière), `liste_attente` (attente), `non_retenu` (+ `motif_communicable` s'il existe, **sinon** message générique **FIXE côté client** `MESSAGE_NON_RETENU_GENERIQUE`), `indisponible` (**D-8b3-3** : nouveau — « Votre candidature a été clôturée. Votre place n'a pas pu être maintenue. […] »). `decision` inattendue (`null`/inconnue) → repli défensif sur le message générique de non-retenue.
- **Stepper « Suivi » = 4 étapes coarse** (`Compte créé` · `Dossier soumis` · `En traitement` · `Résultat`), état dérivé **uniquement** de `statut_public` (**D-8b3-1**). On **ne reproduit PAS** le timeline `Vérification d'éligibilité` / `Instruction` / `Évaluation` / `Entretien` / badge « Non conforme » : chaque jalon trahirait la position interne dans le workflow, autant que la bannière « non éligible ».
- **On ne reproduit PAS** la bannière « Candidature non éligible » (**D-8b3-2**, D-5b-1 déjà acté) : un `non_retenu` est un `non_retenu`, qu'il vienne d'un non-éligible interne ou d'un manque de places. Le backend rend déjà les deux réponses **byte-identiques** ; l'UI ne lit que `decision` + `motif_communicable`, elle ne peut donc pas réintroduire la distinction.
- **Tout le texte affiché vient d'un `switch` PUR** (`resultatMessages.js`) sur `(statutPublic, decision)` → une constante. Zéro arithmétique, zéro seuil, aucun mot d'éligibilité/score/évaluation dans le JSX.
- **Dashboard SOBRE** (**D-8b3-5**) : la maquette calcule une barre `progression %` depuis `statut_interne` — retirée. Un « 66 % qui stagne » inquiète ou fait sur-interpréter ; le stepper communique l'avancement honnêtement. On garde les infos factuelles neutres (badge statut, Documents X/6, filière).
- **Nav latérale** : l'entrée « Ma candidature » devient un vrai lien ; les entrées non branchées (`.sidebar-link.is-inert`) sont **atténuées, curseur par défaut, sans survol** — elles ne doivent pas paraître cliquables (**D-8b3, Q2**).
- **Récapitulatif** : Numéro / Date de soumission / Filière / Cohorte (`campagne.nom`) / Documents X/6. Bouton « Voir mes documents » de la maquette **retiré** (**D-8b3-6** : pas d'écran documents au périmètre).
- **Pas de card « Notifications récentes »** (**D-8b3-4**) : aucune API notifications (point ouvert connu).

**Comment la non-fuite est garantie (et testée).**
1. Le hook n'expose que des primitives, copiées de l'API.
2. Le rendu est un `switch` pur ; le message générique de non-retenue est une **constante client**.
3. Le stepper ne lit que `statut_public`, pas de branche `is-rejected`.
4. **Test Vitest de non-fuite** : pour **chaque** `statut_public × decision × (motif|null)` — y compris avec un payload sali (`statut_interne`, `motif_interne`, `rang`, `score_total` injectés) — `container.textContent` ne matche **aucun** de `/score|rang|barème|éligib|évaluat|note|\/(35|65|100)|points?|pondér|non_eligible|statut_interne|motif_interne/i`.
5. **Test d'indiscernabilité** : `non_retenu` + `motif_communicable:null` avec vs sans champs internes parasites → `container.innerHTML` **strictement identique**. Les deux `non_retenu` (issu d'un non-éligible / ordinaire) produisent le **même DOM**.

**Conséquence.** **Backend strictement inchangé.** Preuve : `vitest` **109 tests** (dont `MaCandidature.test.jsx` — un par `statut_public`, un par `decision`, non-fuite `it.each` sur 8 combos, indiscernabilité DOM ; `resultatMessages.test.js` ; `useMaCandidature.test.js` ; `CandidatDashboard.test.jsx` étendu), E2E `suivi-candidature.spec.js` (base jetable `migrate:fresh` avant/après ; `en cours de traitement` → phrase neutre + 0 jalon interne ; `retenu` / `non_retenu` après publication ; le `non_retenu` d'un non-éligible rendu identiquement), captures `suivi-{en-cours,retenu,non-retenu}` en 390 / 1280, smoke `smoke8b3.sh` (`GET /api/candidature` dans les 3 états, réponse sans `rang` / `motif_interne` / `statut_interne` / `score` même après avoir sali la base ; `non_retenu`-issu-de-non-éligible byte-identique à un `non_retenu` ordinaire).

**Note bundle.** Les termes « éligibilité » / « égalité de score » présents dans le bundle proviennent de la **vitrine publique** (`HomePage`, critères d'élimination + FAQ — Lot 8b-1, formulation déjà arbitrée à l'ADR-18) et de `routes.js`/`navConfig` (`evaluateur`) — **pas** des écrans de suivi, dont le DOM rendu est vérifié propre par le test de non-fuite.

**⚠️ POINT OUVERT INSTITUTIONNEL.** La formulation de **tous les textes candidats** de `resultatMessages.js` (résultats retenu / liste d'attente / non-retenue générique / clôture `indisponible`) relève d'une décision de **communication** — à faire **relire par les partenaires (CCI-CI / FADV / AICS) avant mise en production**, au même titre que les FAQ publiques du Lot 8b-1.

**Divergences maquette.** D-8b3-1 (timeline granulaire non reproduit), D-8b3-2 (« non éligible » non reproduit), D-8b3-3 (`indisponible` : message neuf), D-8b3-4 (pas de notifications), D-8b3-5 (pas de barre %), D-8b3-6 (pas de bouton « documents »).

## ADR-21 — Frontend : espace évaluateur, consultation & vérification (Lot 8c-1)

**Contexte.** Après l'espace candidat complet (8b), on construit l'espace **évaluateur** — une **inversion de posture** : jusqu'ici le front cachait systématiquement la zone 🔴 (statut interne, réponses, critères d'éliminination) ; ici, un rôle a le **droit** de la voir, c'est son travail. Le piège symétrique existe côté maquette : `fiche-candidat.html` **recalcule l'éligibilité côté navigateur** (`checkCriteresEliminatoires`, l.68‑79) — le front NE reproduit PAS ce recalcul, même là où le rôle est autorisé à voir le résultat (ADR‑06 : la logique d'élimination reste 100 % serveur, quel que soit qui la consulte).

**Décision.**
- **Nouvel arbre `pages/evaluateur/`**, strictement étanche de `pages/candidat/`. `optionLabels.js` **duplique** délibérément une partie des libellés de `wizard/formStructure.js` (SC.02, SE.*, expérience, langues, DI.02, SC.04) plutôt que de les importer — un peu de duplication vaut mieux qu'un pont entre deux arbres qui doivent rester étanches. **Garde exécutable** (`noBridge.test.js`) : lit le code source de `pages/evaluateur/**` et échoue si un `import`/`require` référence `pages/candidat` — pas une convention, un test.
- **Dashboard** : 4 KPI (Total / À traiter / En instruction / Évalués) dérivés de `meta.total` de 4 appels `GET /evaluateur/candidatures` filtrés par `statut_interne` — **aucun graphique** (Chart.js hors périmètre), **aucun** duo Éligibles/Non‑éligibles (le backend n'expose pas ce comptage). Deux mini‑listes (« Dossiers prioritaires », « Alertes d'éligibilité ») dérivées des items déjà renvoyés par ces mêmes appels — l'« alerte » filtre sur `statut_eligibilite_interne`, un champ **déjà calculé serveur** : c'est un filtre d'affichage, pas un recalcul.
- **Liste « Mes dossiers »** (`/evaluateur/mes-dossiers`) : **un seul écran**, lié à l'unique endpoint auto‑scopé par le backend (mes dossiers pour un évaluateur, tous les dossiers instructibles pour un administrateur — même écran, même requête, le titre s'adapte). La vue admin de pilotage/affectation en masse (`candidatures.html` de la maquette) n'est **pas** construite ici — reportée au 8d (espace admin).
- **Fiche candidat** (`/evaluateur/candidatures/:id`) : onglets **consultation** (Profil, Scolarité, Socio‑éco, Expérience + téléchargement justificatif, Langues, Motivation — **sans** `mo04_note_etoiles`, Disponibilité, Documents + téléchargement) + panneau **Éligibilité** qui n'affiche QUE `statut_eligibilite_interne` et `criteres_eliminatoires[].detail` — le `detail` est une phrase **déjà rédigée serveur** (`ServiceEligibilite`), rendue telle quelle, jamais reconstruite. **Aucun onglet Évaluation/Entretien, aucun score affiché** (8c‑2) ; seul un badge booléen « Dossier verrouillé » (état de workflow, pas un score) figure dans l'en‑tête.
- **Vérification** (`PUT .../verification`, onglet dédié) : nationalité confirmée + SC.04 diplôme (libellés + hint verbatim `scoring.js`, **sans les points** — même discipline que `formStructure.js`). **Actif seulement si `statut_interne === 'en_instruction'`** (miroir exact de la garde backend, `<fieldset disabled>` sinon + message explicatif ; un 409 tardif affiche le message serveur tel quel). **La réponse du PUT EST la ressource fraîche** : le panneau Éligibilité se re‑rend depuis cette réponse, sans refetch ni recalcul — le hook `useFicheCandidat` remplace l'état local intégralement.
- **Rebranchement admin ⊇ évaluateur (ADR‑10, reporté au 8a)** : les routes `/evaluateur/*` passent de `roles={['evaluateur']}` à `roles={['evaluateur','administrateur']}` (`/admin/*` reste `['administrateur']` seul — pas de symétrie). **`AppShell` gagne un prop `space`** (replie sur `role` si absent) : un écran évaluateur passe `space="evaluateur"` explicitement, de sorte qu'un administrateur en recouvrement voit la **sidebar évaluateur** (où il est) tandis que le pied de sidebar continue d'afficher son **vrai rôle** — « Administrateur » (qui il est). Sans ce prop, l'admin verrait la sidebar admin (campagnes, classement…) sur un écran évaluateur, source de confusion.

**Conséquence.** **Backend strictement inchangé** (Lot 4a déjà complet). Preuve : `vitest` **136 tests (+27)** (`FicheCandidat.test.jsx` : zone 🔴 rendue, `detail` serveur affiché tel quel, **vérification diplome=cepe → panneau Éligibilité reflète la réponse du PUT en un seul appel réseau, zéro refetch** ; `DossiersList.test.jsx` ; `noBridge.test.js` — 10 fichiers vérifiés ; `AppShell.test.jsx` — `space` ; `ProtectedRoute.test.jsx` étendu — candidat rejeté, évaluateur admis, **administrateur admis (recouvrement)**, évaluateur toujours rejeté sur `/admin`), E2E `evaluateur.spec.js` (réutilise `DemoClassementSeeder` + un simple `UPDATE` PSQL rouvrant un dossier `en_instruction` — pas de script de seed dédié : candidat redirigé → évaluateur consulte sa fiche → vérification CEPE reflétée en direct → **administrateur accède à la même fiche, recouvrement prouvé**), captures `evaluateur-{dashboard,liste,fiche,verification,critere-reflete,admin-recouvrement}` en 390/1280, smoke `smoke8c1.sh` (liste auto‑scopée évaluateur vs admin, fiche 404 pour un évaluateur non affecté / 200 pour l'affecté et l'admin / 403 pour un candidat, vérification → critère reflété **dans la même réponse** puis confirmé par un second GET, 409 sur un dossier non `en_instruction`).

**Note bundle.** Contrairement à l'espace candidat, il est **normal** que le bundle évaluateur contienne des libellés de grille (SC.04, options de réponses) — l'évaluateur les affiche légitimement. Aucune **valeur** de barème (points, poids) n'y figure : `optionLabels.js` ne transcrit que des libellés, jamais les points `scoring.js` (cepe:0, cap:0, bepc:1.5, bac:3, bt_bep:3) — mentionnés une seule fois, en commentaire, pour justifier leur absence.

**Divergences maquette.** D‑8c1‑1 : pas de graphiques Chart.js (KPI chiffrés + mini‑listes uniquement). D‑8c1‑2 : KPI « Éligibles/Non‑éligibles » remplacés par « En instruction/Évalués » (le backend ne filtre pas par éligibilité en comptage). D‑8c1‑3 : la vue admin « Candidatures » (bulk affectation) de la maquette n'est pas construite — reportée au 8d. D‑8c1‑4 : pas d'onglet Évaluation/Entretien ni de score dans la fiche (8c‑2).

## ADR-22 — Frontend : notation dossier /65 + entretien /35, verrouillage réel (Lot 8c-2)

**Contexte.** Le 8c-1 a livré la consultation & vérification ; il reste la **notation** — la dernière zone où la maquette recalcule un score côté navigateur (`evaluation.html`/`entretien.html`, `window.CasaScoring.computeScores`/`computeEntretienScore`, rappelées à **chaque clic** sur un sélecteur). C'est le piège symétrique de celui déjoué au 8c-1 pour l'éligibilité (ADR-21) : ici le rôle a le droit de VOIR *et de saisir* un score, mais jamais de le CALCULER.

**Décision.**
- **Deux écrans dédiés** (`/evaluateur/candidatures/:id/evaluation`, `/evaluateur/candidatures/:id/entretien`), atteints par des boutons sur l'en-tête de la fiche (8c-1) — pas deux onglets de plus dans une fiche déjà à 9 onglets. Séparent consultation (fiche) et notation (ces écrans), comme la maquette.
- **Le score AFFICHÉ vient TOUJOURS de la réponse serveur** (ADR-02, ADR-04) : `useEvaluationDossier`/`useEntretien` REMPLACENT intégralement leur état par la réponse de chaque `GET`/`PUT`/`POST` — aucun total, pourcentage de rubrique ou note n'est calculé en JS. La seule arithmétique tolérée est un ratio D'AFFICHAGE (angle de l'anneau SVG, largeur en % d'une mini-barre, dans `ScoreRing`) dérivé de deux nombres déjà connus (`score_obtenu`/`max`) — jamais une note, jamais persisté.
- **Différence structurelle avec le 8c-1** : `GET .../evaluation` et `GET .../entretien` embarquent déjà `label` **et** `max` par rubrique/sous-critère (`ServiceScoring` les lit en base) — contrairement à `optionLabels.js` (8c-1, nécessaire car ces libellés n'existent dans AUCUNE réponse API), ces écrans n'ont besoin d'**aucune** constante de barème : `PointPicker` construit sa plage `0..max` dynamiquement depuis la valeur API de CE sous-critère, jamais d'une constante partagée. Seules exceptions tolérées, aucune des deux n'étant un point de barème : la plage FIXE 0-5 du sélecteur d'étoiles MO.04 (cardinalité d'UI, miroir de la règle backend `between:0,5` — pas la valeur en points d'une étoile, qui reste 100 % serveur), et les 2 libellés de lieu d'entretien (noms de site, miroir de `Rule::in([...])`).
- **D-8c2-1 (divergence majeure).** La maquette laisse l'évaluateur **ré-éditer** les réponses SC/SE/DI déclarées par le candidat directement sur l'écran de notation dossier, avec recalcul JS à chaque clic. Le backend (`EnregistrerEvaluationRequest`) n'accepte que `mo04_note_etoiles` + `commentaire_evaluateur` (D-4b-2 : « l'évaluateur ne réajuste pas les réponses candidat »). L'UI suit la règle **backend**, pas la maquette : seule la Motivation (lettre en lecture seule + étoiles + commentaire) est éditable ; les 5 autres rubriques n'apparaissent que via leur SCORE agrégé (`ScoreRing`) — la consultation détaillée des réponses reste sur la fiche (8c-1), à un clic (« Voir la fiche complète »).
- **Verrouillage visuel RÉEL** (ADR-04) : `<fieldset disabled={!editable}>` désactive NATIVEMENT tous les champs après validation (pas un grisage CSS — `pointer-events`/lecture seule contournables) ; les boutons Enregistrer/Valider sont REMPLACÉS (jamais simplement masqués) par une bannière 🔒 (« ÉVALUATION VALIDÉE » / « ENTRETIEN VALIDÉ ») portant la date et l'auteur. La réponse du `POST .../validation` **est** le snapshot figé — remplace l'état local intégralement, même patron de reflet direct qu'au 8c-1 (zéro refetch). Toute tentative résiduelle échouerait de toute façon en 409 côté serveur, mais l'UI ne laisse jamais l'utilisateur la déclencher.
- **Préconditions reflétées, jamais recalculées** : dossier — vérification incomplète (`nationalite_confirmee`/`diplome_verifie` non renseignés) ou `mo04_note_etoiles` absente → bouton « Valider » désactivé + message, dérivés des données déjà chargées (aucun appel réseau supplémentaire, `useFicheCandidat` déjà appelé pour la lettre de motivation) ; `statut_interne !== 'en_instruction'` → formulaire non proposé (miroir du 409) ; entretien — `dossier_verrouille === false` → empty-state, aucun formulaire (miroir du 409, précondition Lot 4b) ; `presence === 'absent'` → sous-notes désactivées à 0 et **jamais envoyées** dans le `PUT` (le backend renvoie 422 si `notes` est présent avec `presence !== 'present'`) ; `presence` non renseignée → « Valider » désactivé (le backend l'exige aussi, 422). Une sur-notation (sous-note excédant `max`) reste un 422 explicite du backend, affiché tel quel — jamais de clamp silencieux côté client, même si `PointPicker` la rend déjà improbable en usage normal (plage bornée par l'API).
- **Panneau Éligibilité partagé** (`EligibilitePanel`, extrait de la fiche 8c-1 vers un composant réutilisé entre écrans évaluateur) : reste dans `pages/evaluateur/` — jamais remonté dans `components/` — pour que la garde de non-pont continue de porter sur tout l'arbre. Zéro appel réseau supplémentaire : `useFicheCandidat`, déjà appelé pour l'identité/la lettre de motivation, fournit aussi `statut_eligibilite_interne`/`criteres_eliminatoires`.

**Conséquence.** **Backend strictement inchangé** (Lots 4b/4c déjà complets). Preuve : `vitest` **183 tests (+47)** — `EvaluationDossier.test.jsx` (aperçu affiché tel quel, saisie → `PUT` → nouvel aperçu affiché, validation → verrouillage natif **fieldset** + bannière + snapshot, 422 de validation affiché, préconditions vérification/note/`en_instruction`) ; `Entretien.test.jsx` (précondition dossier non verrouillé → empty-state sans appel d'écriture, planification → `PUT` crée l'entretien, sélecteurs de sous-notes bornés par `max` **de l'API** sans aucune constante locale, présence Présent/Absent → `notes` envoyées ou non, sous-note hors max → 422 affiché, validation → verrouillage) ; `noScoringFormula.test.js` (scan statique du source `pages/evaluateur/**`, commentaires exclus, contre les motifs `/65`, `/35`, `pointsParEtoile`, `barème`, `CasaScoring`, `computeScores*` — la plage d'étoiles 0-5 whitelistée nommément). E2E `notation.spec.js` (noter le dossier → valider → verrouillé ; planifier + noter un entretien → valider → verrouillé) + captures 390/1280, smoke `curl` contre le **bundle de production reconstruit** (grep zéro terme de barème/formule dans le JS servi, pas seulement le source) + parcours complet des préconditions/verrouillages (422 vérification, 422 note absente, 422 sur-notation, 409 après verrouillage dossier et entretien, recouvrement admin).

**Divergences maquette.** D-8c2-1 (pas de ré-édition des réponses SC/SE/DI candidates sur l'écran de notation — seule la Motivation est éditable, D-4b-2). D-8c2-2 (le score final /100 combinant dossier+entretien, affiché par la maquette sur l'écran entretien, n'est renvoyé par AUCUNE des deux réponses API 4b/4c prises séparément — non affiché ici, cohérent avec l'absence de classement/100 déjà actée aux ADR précédents ; matière du Lot 5a en interne, jamais exposée à l'évaluateur). D-8c2-3 (pas de listes `Évaluations`/`Entretiens` dédiées — entrées sidebar toujours inertes, D-8c1 ; chaque dossier reste atteignable via Mes dossiers → fiche → boutons de notation). D-8c2-4 (pas de correction exceptionnelle — espace admin, 8d).

## ADR-23 — Frontend : espace admin, supervision & gestion courante (Lot 8d-1)

**Contexte.** Dernier espace du frontend. Le Lot 6a a livré 6 endpoints administrateur-strict (affectation, supervision candidatures, filières, campagnes, audit) mais **aucun point de lecture** pour lister les campagnes ni les évaluateurs — un manque resté invisible tant qu'aucun écran ne s'appuyait dessus. La maquette (`candidatures.html`, `cqp.html`, `campagnes.html`, `audit.html`, `dashboard.html`) propose trois actions sans contrepartie backend (« Marquer éliminé » = Lot 6b/8d-3 ; « Modifier » une filière et « Nouvelle campagne » = D-6a-2, jamais implémentées) et une recherche d'audit dont le placeholder (« Rechercher un auteur, une action… ») ment sur ce qu'elle couvre réellement côté serveur.

**Décision.**
- **Deux trous d'API comblés, minimalement** (Étape 1, Q1) : `GET /api/admin/campagnes` (ajouté à `CampagneController`, Lot 6a) et `GET /api/admin/evaluateurs` (nouveau `EvaluateurController`), tous deux administrateur-strict, non paginés (populations réduites). Chacun a sa **liste blanche verrouillée par test**, même discipline que `FilieresPubliquesTest` (8b-2) : `CampagneResource` → `id/nom/statut/date_ouverture/date_cloture/places_totales` (jamais `description`, jamais la relation `filieres`/`publication`) ; `EvaluateurResource` → `id/prenom/nom/poste` (jamais l'e-mail, jamais `utilisateur_id`). Les deux servent À LA FOIS l'écran dédié et les filtres `?campagne=`/`?evaluateur=` de la vue supervision — pas de troisième point de lecture.
- **Vue candidatures + affectation** (`CandidaturesSupervision.jsx`, la vue reportée du 8c-1) : tableau à cases à cocher sur `CandidatureAdminResource` (statut interne, éligibilité, scores figés, décision — 🔴 LÉGITIME ici, jamais recalculée), 4 filtres (statut/filière/évaluateur/campagne). L'affectation en masse (`AssignModal.jsx`) est **ATOMIQUE côté serveur** (Lot 6a) : le 422 (liste des dossiers refusés, numéros inclus) est affiché **verbatim** dans le modal, qui **ne se ferme pas** et **ne vide pas la sélection** — l'utilisateur ajuste et réessaie sans tout reprendre. Le bouton « Marquer éliminé » de la maquette n'est **pas construit** (acte exceptionnel, Lot 6b/8d-3, D-8d1-1).
- **Continuité de navigation admin ⊇ évaluateur** (Étape 1, Q5) : le lien « Voir » renvoie vers la fiche évaluateur **existante** (`/evaluateur/candidatures/:id`, recouvrement ADR-10 acquis au 8c-1) — pas de fiche admin dédiée. Mais la fiche et les écrans de notation (8c-2) avaient un breadcrumb « Mes dossiers » **fixe** vers `/evaluateur/mes-dossiers` : un admin arrivant depuis `/admin/candidatures` s'y serait retrouvé « perdu » dans un espace qui n'est pas le sien. `retourListePath(role)`/`retourListeLabel(role)` (nouveaux, `routing/routes.js`, neutres — importés par les trois arbres sans les relier entre eux) rendent ce retour dépendant du **rôle réel** : `/admin/candidatures` pour un administrateur, `/evaluateur/mes-dossiers` sinon — appliqué aux 3 écrans concernés (`FicheCandidat`, `EvaluationDossier`, `Entretien`).
- **Filières** (`Filieres.jsx`) : la liste réutilise `GET /api/filieres` **public** (8b-1/8b-2) — `actif` y est déjà exposé, un second point de lecture admin serait redondant. Seul le switch est réel (`PATCH /admin/filieres/{id}`). Pas d'édition nom/description/quota, pas de création (D-6a-2 — le bouton « Ajouter » est `disabled` jusque dans la maquette elle-même, D-8d1-2).
- **Campagnes** (`Campagnes.jsx`) : liste depuis le nouvel endpoint ; les boutons Ouvrir/Clôturer dépendent **uniquement** de `statut` renvoyé par l'API (aucune matrice de transition devinée côté client). Clôturer étant **irréversible** (`TRANSITIONS['cloturee'] = []` côté backend), une confirmation (`pages/admin/ConfirmDialog.jsx`, dupliqué de celui du 8c-2 — cf. non-pont) précède les deux transitions ; le 409 « une autre campagne déjà ouverte » et le 422 hors matrice s'affichent verbatim. Pas de bouton « Nouvelle campagne » (D-6a-2, D-8d1-3).
- **Audit** (`Audit.jsx`) : la zone 🔴 (`ancienne_valeur`/`nouvelle_valeur`/`motif`) est affichée **telle quelle** — c'est l'outil de supervision de l'administrateur. **`recherche` est un champ SÉPARÉ de `auteur`** (Étape 1, Q4) : le premier part tel quel vers `?recherche=` (borné côté serveur à `action`+`objet`, `AuditController`, Lot 6a) avec un placeholder **honnête** (« Rechercher une action, un objet… », pas « … un auteur » comme le laisse croire la maquette) ; le second part vers `?auteur=` (égalité exacte e-mail). **Aucun filtre client** n'est appliqué sur `ancienne_valeur`/`nouvelle_valeur`/`motif` — vérifié par un test qui observe la requête envoyée, jamais un filtrage local du résultat reçu.
- **Dashboard** (`AdminDashboard.jsx`) : 4 KPI = `meta.total` de 4 appels `GET /admin/candidatures` filtrés (dont `?evaluateur=non_affecte`, un filtre déjà supporté) + une carte Campagnes (nouvel endpoint) — même sobriété qu'au 8c-1 (D-8c1-1/2) : pas de Chart.js, pas de taux d'éligibilité/sélection ni de KPI « Utilisateurs »/« Places totales » (non dérivables des filtres exposés par le backend).
- **Garde de non-pont rendue SYMÉTRIQUE sur les trois arbres** (Étape 1, Q6) : `pages/admin/__tests__/noBridge.test.js` (nouveau, interdit `pages/candidat`/`pages/evaluateur`), `pages/evaluateur/__tests__/noBridge.test.js` (étendu, interdit désormais aussi `pages/admin`), `pages/candidat/__tests__/noBridge.test.js` (nouveau, interdit `pages/evaluateur`/`pages/admin` — l'arbre candidat n'avait encore aucun garde-fou explicite). `pages/admin/optionLabels.js` et `pages/admin/ConfirmDialog.jsx` **dupliquent** volontairement leurs équivalents évaluateur plutôt que de les importer.

**Conséquence.** Backend : **2 endpoints de lecture ajoutés** (`GET /admin/campagnes`, `GET /admin/evaluateurs`), listes blanches testées, reste du contrat Lot 6a inchangé. Preuve backend : `php artisan test` **302 (+6)** — `CampagnesListeTest`, `EvaluateursListeTest` (listes + liste blanche verrouillée + 403 hors admin). Preuve frontend : `vitest` **241 (+58)** — `CandidaturesSupervision.test.jsx` (affectation atomique reflétée : succès vide la sélection et recharge, 422 affiche le message verbatim et **préserve** la sélection), `Filieres.test.jsx`, `Campagnes.test.jsx` (transitions + 409/422 verbatim), `Audit.test.jsx` (requête envoyée observée — jamais de filtrage local du 🔴), `AdminDashboard.test.jsx`, `ProtectedRoute.test.jsx` étendu (évaluateur ET candidat rejetés des 4 écrans admin concrets, pas seulement du préfixe générique), 3× `noBridge.test.js` symétriques. E2E `admin.spec.js` (évaluateur rejeté → dashboard → affecter Awa à Solange N'Dri → toggle filière → consulter l'audit filtré) + captures 390/1280, smoke `curl` (listes blanches, affectation atomique avec dossier réellement non affecté après le 422, filière reflétée sur l'endpoint public, garde-fou campagne 409/422, recherche d'audit bornée, 403 sur les 4 endpoints pour évaluateur et candidat).

**Divergences maquette.** D-8d1-1 (pas de « Marquer éliminé » — acte exceptionnel, 8d-3). D-8d1-2 (pas d'édition nom/description/quota de filière, pas de création — D-6a-2, hors backend). D-8d1-3 (pas de création de campagne — même raison). D-8d1-4 (placeholder de recherche d'audit reformulé pour rester honnête sur le bornage serveur, au lieu de laisser croire qu'il couvre l'auteur). D-8d1-5 (dashboard sans Chart.js ni taux calculés, même choix qu'au 8c-1).

## ADR-24 — Frontend : classement & publication (Lot 8d-2)

**Contexte.** Dernier écran de supervision et acte le plus lourd de conséquences de toute l'application : le classement expose `score_final`/`rang`/`motif_interne` (🔴 absolu, jamais vus ailleurs) et la publication bascule irréversiblement la visibilité de la décision pour tous les candidats d'une campagne (ADR-08 : publication 1-1 par campagne, pas un flag global). La maquette (`admin/classement.html`) calcule classement et score final en JS (`rankCandidatsParFiliere`, `computeScoreFinal`) — piège déjà déjoué au 8c-2 pour la notation, reconduit ici pour le classement.

**Décision.**
- **Écran dédié** `/admin/classement/:campagneId` (sélecteur de campagne, lien « Voir le classement » ajouté sur `Campagnes.jsx`, Étape 1 Q1) ; sans id dans l'URL, `<Navigate>` **déclaratif** (pas `navigate()` impératif pendant le rendu — anti-pattern React) vers la campagne la plus récente, déjà triée serveur par `useCampagnes()` (8d-1), aucun tri client.
- **`score_final`, `rang`, `departage` viennent TOUJOURS de `ClassementResource`** : `useClassement` remplace intégralement son état à chaque réponse. Les `lignes[]` arrivent **déjà triées** par le serveur — l'écran ne fait **aucun** `.sort()`, garanti par un test statique (`noScoringFormula.test.js`, dupliqué du 8c-2 sur l'arbre admin) qui vérifie l'ABSENCE de `.sort(` et la présence du rendu direct depuis `filiereActive.lignes`. **Départage affiché en clair** (Étape 1 Q2, requis par le périmètre) : résumé compact (mixité/vulnérabilité/secteur/motivation) sous chaque score, visible en permanence — pas au survol, pour rester lisible sur mobile.
- **Score dossier/entretien affichés SANS dénominateur codé en dur** (`Dossier 60.0 · Entretien 28.0`, pas `60.0/65`) : leurs maxima (65/35) ne sont pas dans `ClassementResource` — les coder en dur réintroduirait un poids de barème que le 8c-2 avait justement banni. Seule exception assumée : le littéral `/ 100` pour `score_final`, qui n'est **pas** un poids de grille mais un plafond FIXE du système (`ServiceClassement::scoreFinal()` : `min(..., 100.0)`, indépendant des poids de volet) — documenté et distingué explicitement dans le test statique.
- **Distinction motif interne (🔴) / communicable (🟡)** rendue **impossible à confondre** : deux bandeaux `Alert` de couleurs et libellés différents (« confidentiel, jamais visible » vs « visible par le candidat après publication »), reproduisant le texte exact de la maquette sur le message générique par défaut. **Étendu à `liste_attente` en plus de `non_retenu`** (Étape 1 Q5 — le contrat de `PUT .../decision/motifs` ne restreint par aucune décision, vérifié dans le code AVANT d'étendre) ; toujours absent sur `retenu`.
- **Friction délibérée à la publication** (Étape 1 Q4, au-delà d'un `ConfirmDialog` standard jugé disproportionné pour cet acte) : `PublishConfirmDialog.jsx` exige de **taper le nom exact de la campagne** avant d'activer le bouton « Publier définitivement » (pattern GitHub/Stripe pour les actes destructeurs) — empêche le clic réflexe, force à lire QUELLE campagne on publie. Le texte du bandeau reprend mot pour mot l'irréversibilité (« aucune dé-publication »).
- **État « déjà publié » = consultation stricte** : `publie:true` retire Calculer/Recalculer/Publier/Motif (disparus, pas grisés — même discipline « verrouillage réel » qu'au 8c-2/8d-1), remplacés par un bandeau 🔒 avec la date et l'auteur ; le classement reste **visible**.
- **Petit complément backend** (comme les 2 endpoints du 8d-1) : `publiee_le`/`publiee_par` ajoutés à `GET .../classement` (Étape 1 Q3) — `POST .../publier` renvoie un `PublicationResource` différent (pas de `filieres`), donc après cet appel le hook **recharge** `GET .../classement` plutôt que d'injecter directement la réponse du POST ; ce même GET, rejoué à un rechargement de page, retrouve la traçabilité complète (avant cet ajout, elle ne survivait qu'en mémoire locale). Liste blanche : le **nom** de l'auteur, jamais son e-mail (`MembreEquipe`, pas `User`).
- **CSS dupliqué, pas partagé** : `.lock-banner` (déjà écrit pour le 8c-2 dans `pages/evaluateur/Notation.css`) est recopié dans `pages/admin/Classement.css` plutôt qu'importé depuis l'arbre évaluateur — la garde de non-pont (8d-1, désormais symétrique) porte aussi sur les fichiers `.css`, pas seulement le JS.
- **Hors périmètre, exclu explicitement** (Étape 1 Q6) : bouton « Déclarer indisponible » de la maquette (remplacement post-publication, acte exceptionnel — Lot 6b/8d-3) ; bouton « Exporter » (aucun endpoint backend — **point ouvert**, probablement un lot ultérieur si un export de rapports est demandé).

**Conséquence.** Backend : **1 complément** (`publiee_le`/`publiee_par` sur `GET .../classement`), reste du contrat Lots 5a/5b inchangé. Preuve backend : `php artisan test` **303 (+1)** — nouveau test dans `PublicationTest` prouvant que ces deux champs sont absents avant publication et survivent à un **second** appel GET indépendant (pas la réponse du POST) après, liste blanche vérifiée (aucun e-mail dans la réponse). Preuve frontend : `vitest` **280 (+39)** — `Classement.test.jsx` (score/rang/départage affichés tels quels, calcul idempotent avec bouton Calculer→Recalculer, modal Motif aux deux libellés distincts + absent sur `retenu`/présent sur `liste_attente`+`non_retenu`, publication exigeant la saisie exacte du nom avant d'activer le bouton, 422 précondition, état publié sans aucune action), `noScoringFormula.test.js` dupliqué sur l'arbre admin. E2E `classement.spec.js` sur **base jetable** (`migrate:fresh` avant/après — la publication est irréversible, même précaution qu'au 8b-3) : calculer → motif sur un candidat non éligible (`non_retenu` réel, sans épuiser de quota) → publier avec la friction (nom incorrect → bouton reste désactivé) → état publié, **y compris après un F5** (preuve directe de l'ajout `publiee_le`/`publiee_par`) + captures 390/1280. Smoke `curl` contre le bundle de **production** reconstruit (zéro `CasaScoring`/`computeScoreFinal`/`rankCandidatsParFiliere`/`TAILLE_LISTE_ATTENTE`), idempotence + préservation des motifs au recalcul, 422/409 sur la publication, 403 sur les 4 endpoints pour évaluateur et candidat.

**Divergences maquette.** D-8d2-1 (pas de « Déclarer indisponible » — acte exceptionnel, 8d-3). D-8d2-2 (pas de bouton « Exporter » — aucun endpoint, point ouvert). D-8d2-3 (départage affiché en résumé compact permanent, pas les 4 colonnes séparées ni un survol — table dense, lisibilité mobile). D-8d2-4 (friction de publication renforcée — saisie du nom exact — au lieu du simple `Annuler/Publier` de la maquette, disproportionné pour cet acte).

## ADR-25 — Frontend : actes exceptionnels — correction, remplacement, élimination (Lot 8d-3)

**Contexte.** Dernier sous-lot fonctionnel de l'espace admin : donner une interface aux trois gestes d'ADR-15/Lot 6b, les seuls du système à casser délibérément un invariant (rouvrir un verrou ADR-04, rétrograder/promouvoir une décision publiée, forcer une inéligibilité hors `ServiceEligibilite`). Le backend est **entièrement livré et testé** depuis le Lot 6b (`CorrectionController`, `RemplacementController`, `EliminationController`, 26 tests `Feature/Admin/*`) : ce lot n'ajoute **aucun** endpoint ni migration, seulement l'UI et sa preuve d'intégration.

**Décision.**
- **Motif obligatoire réellement bloquant** sur les trois actes : un composant partagé par contenu — `MotifConfirmDialog.jsx` (remplacement, élimination) — désactive son bouton de confirmation tant que `motif.trim().length < 3` (miroir exact de `min:3` côté `Request`), le 422 serveur restant le dernier rempart si la course arrive quand même. **Dupliqué** dans `pages/admin/` et `pages/evaluateur/` (Étape 1 Q2) plutôt que remonté en composant partagé : l'élimination s'ouvre depuis les DEUX arbres (`CandidaturesSupervision.jsx` et `FicheCandidat.jsx`) sans jamais créer de pont entre eux — garde de non-pont (8d-1) toujours symétrique après l'ajout.
- **Correction exceptionnelle** — bandeau explicite (« Vous rouvrez une évaluation validée / un entretien validé… ») avant tout champ, disponible depuis l'écran de notation verrouillé (`EvaluationDossier.jsx`/`Entretien.jsx`), **administrateur uniquement** (`isAdmin` dérivé de `role`, jamais un nouveau rôle). Réponse POST de forme différente d'un `EvaluationDossierResource`/`EntretienResource` (`{numero_dossier, score_*, champs_modifies}`, pas de `rubriques`) : le hook `useCorrection` ne l'injecte **jamais** dans l'état de notation — l'appelant recharge (`reload()` des hooks `useEvaluationDossier`/`useEntretien`, + `useFicheCandidat` pour le dossier puisque l'éligibilité a pu changer), même patron que la publication au 8d-2. **Aucune pré-vérification de publication côté client** (Étape 1 Q3) : le bouton reste proposé même après publication, le 409 backend s'affiche verbatim dans le modal qui reste ouvert — le client guide, le serveur décide.
  - **Portée volontairement ciblée** (Étape 1 Q1, **point ouvert explicite** — cf. ci-dessous) : `CorrectionDossierModal.jsx` ne couvre que nationalité + SC.04 (diplôme) + MO.04 (étoiles) + commentaire, alors que le backend (`CorrigerDossierRequest`) accepte l'intégralité de `reponses.*` (toute auto-déclaration candidat SC/SE/DI/langues/expériences). `CorrectionEntretienModal.jsx`, lui, a une parité **complète** avec la notation normale (12 sous-notes + observation) — la surface backend de l'entretien correspond exactement à ce qui est déjà noté, pas de réduction à faire.
- **Remplacement** — accessible uniquement sur une ligne `retenu` d'un classement **publié** (`data.publie && l.decision === 'retenu'`, précondition purement indicative, le 422 serveur reste autoritaire). Le candidat **promu** est montré AVANT confirmation : une **lecture** (pas un recalcul) du premier `liste_attente` de la filière **active** dans `lignes[]`, déjà trié par rang par le serveur — présentée comme un aperçu « sous réserve » (Étape 1 Q4), car `RemplacementController` sélectionne exactement de la même façon (même filière, `orderBy('rang')`). Le résultat **définitif** (`{indisponible, promu}`) vient de la réponse POST et remplace l'aperçu dans la bannière affichée ensuite ; la réponse n'ayant pas la forme d'un `ClassementResource`, l'écran **recharge** (`reload()`) plutôt que de fusionner l'état localement. `decision = 'indisponible'` reçoit son propre libellé (« Indisponible », badge neutre) dans `DECISION_LABEL`/`DECISION_BADGE` — jusque-là seuls `retenu`/`liste_attente`/`non_retenu` y figuraient.
- **Élimination manuelle** — **mono-cible** partout (D-6b-4, aucun endpoint bulk) : contrairement au bouton « Marquer éliminé » **en masse** de `candidatures.html`, `CandidaturesSupervision.jsx` propose un bouton par ligne (Étape 1 Q5, assumé : un acte grave se décide individuellement). Accessible aussi depuis `FicheCandidat.jsx` (évaluateur ⊇ admin, Étape 1 Q6 — chaque acte là où l'admin a le contexte). Désactivé avec info-bulle si `statut_eligibilite_interne === 'non_eligible'` déjà.
- **Aucune fuite vers le candidat** (règle reine) : garantie **serveur** au Lot 6b (`test_le_promu_voit_retenu_et_le_sortant_indisponible_sans_rien_d_autre`, `test_apres_publication_indiscernable_d_un_non_retenu_ordinaire`) — ce lot n'y touche pas et le confirme par un test `Classement.test.jsx` dédié : la bannière de résultat, même côté ADMIN, ne mentionne jamais rang ni score, seulement des numéros de dossier.

**Conséquence.** Aucun changement backend (Lot 6b inchangé) — les 26 tests `Feature/Admin/{CorrectionExceptionnelleTest,RemplacementTest,EliminationManuelleTest}` (179 assertions) ont été rejoués en régression et restent verts. Frontend : `vitest` **321 (+23)** — motif bloquant sur les 3 actes (dossier, entretien, remplacement, élimination × 2 arbres), bannière de correction + re-GET + 409 verbatim, préconditions reflétées (verrouillé/retenu+publié/déjà non éligible), aperçu vs résultat réel du remplacement, libellé « Indisponible » dédié, non-fuite. Les 3 `noBridge.test.js` restent verts avec les nouveaux fichiers dupliqués comptabilisés (25/25/20). **Point ouvert, VISIBLE et non enterré (Étape 1 Q1).** La correction exceptionnelle du dossier ne couvre pas encore la correction des auto-déclarations candidat (SC.01-09, SE.01-06, DI.01-03, langues, expériences) — le backend les accepte déjà intégralement (`CorrigerDossierRequest::reponses()`), c'est un choix d'UI assumé : sur les dossiers réels, les corrections fréquentes portent sur le diplôme **vérifié** et la note qualitative (ce que l'évaluateur constate), pas sur une déclaration candidat — l'essentiel du besoin à faible coût d'implémentation. Le cas d'usage central visé par cette portée complète (rectifier une erreur candidat constatée sur pièce, ex. un SC.02 mal renseigné) reste à construire dans un lot ultérieur.

## ADR-26 — Élucidation du 419 CSRF + parcours d'intégration bout-en-bout (Lot 9a)

**Contexte.** Frontend et backend complets (Lots 0 → 8d-3), chaque tronçon testé isolément. Deux objectifs avant d'ouvrir la phase déploiement : (1) lever l'inconnue du `419 CSRF` laissée ouverte au 8d-3 — inconnue sur le composant d'**auth**, inacceptable à l'approche du déploiement ; (2) prouver que la chaîne **entière** (~30 lots) tient d'un bout à l'autre, sur la stack Docker réelle, en une session enchaînée.

**Décision — P1 : le 419 est un artefact `curl`, prouvé par bisection.** `scratchpad/csrf419.sh` rejoue la séquence de 7 requêtes mutantes admin qui échouait (login → correction → classement → publication → 409 → remplacement → élimination), **jar `curl` partagé + relecture du `XSRF-TOKEN` à chaque étape**, en 3 variantes :

| Décodage du token | Header | Résultat |
|---|---|---|
| `perl -pe 's/%([0-9A-Fa-f]{2})/chr hex $1/ge'` (pattern de tous les smokes ≤ 8d-2) | `Origin` | **tout vert** |
| `perl` | `Referer` | **tout vert** (⇒ `Origin`/`Referer` hors sujet) |
| bash `printf '%b' "${v//%/\\\\x}"` (idiome du 1ᵉʳ `smoke8d3.sh`) | `Origin` | **419 partout, login inclus** |

**Cause exacte.** L'idiome bash de décodage URL est fragile au nombre de couches de quoting : **dans un fichier de script** (une couche de plus qu'en `bash -c`), `\\\\x` se réduit à `\\x` et `printf %b` émet la chaîne **littérale** `\x2B\x2F\x3D…` au lieu des octets `+ / =` → `X-XSRF-TOKEN` corrompu, rejeté systématiquement. **Rien à corriger côté app** : la session Sanctum et le token CSRF s'enchaînent parfaitement (le cookie `XSRF-TOKEN` change de ciphertext à chaque réponse — IV aléatoire — mais encode le même token de session stable, qu'un client correct relit sans peine). Le navigateur (E2E) et tout client HTTP correct ne sont pas concernés ; **un admin en production qui enchaîne des actes n'a aucun risque de 419 de ce type**. Couverture curl des actes exceptionnels restaurée : `scratchpad/smoke8d3.sh` refait sur `perl` (**34 OK / 0 FAIL**, deux runs). Point ouvert `419` d'ADR.md → **rayé**. Commit `7434980`.

**Décision — P2 : `frontend/e2e/integration.spec.js`, deux parcours, on-demande.**
- **Tag `@integration`** : `npm run e2e` (filet quotidien, ~15 min) l'**exclut** (`--grep-invert @integration`) ; `npm run e2e:integration` le lance (chaîne complète, avant déploiement / en CI au 9c). Tourne sur le projet `desktop` seul (le helper `shots()` bascule déjà le viewport 390/1280 ; les variables de module `freshEmail`/`freshId` ne survivraient pas à un 2ᵉ passage de projet — `testIgnore` ajouté au projet `mobile`). **Base jetable** : `migrate:fresh --seed` + `cache:clear` avant ET après chaque `describe`.
- **Describe A — parcours nominal complet + RÈGLE REINE** (6 tests serial) : un **vrai candidat frais** (« Nadia Intégration », mot de passe conforme `min:10` — distinct des comptes démo, cf. ci-dessous) s'inscrit → wizard 10 étapes (réponses éligibles) → upload PDF/PNG → soumission (capture) ; l'admin l'**affecte** à l'évaluateur `evaluateur@casa-demo.ci` ; l'évaluateur **vérifie** (nationalité + diplôme BEPC) → **note le dossier /65** → valide (verrouillage) → **planifie + note l'entretien /35** → valide ; **avant publication**, le candidat frais ET Sekou (non-éligible seedé) voient « en cours de traitement », DOM vérifié sans terme interne ; l'admin **calcule le classement** (candidat frais + 6 démo ensemble) → **publie** avec la friction (saisie du nom exact — capture) ; **après publication**, le candidat frais est **retenu** (capture), Sekou voit un **non-retenu générique**, `innerHTML` byte-vérifié : aucune trace d'inéligibilité (capture). Les deux captures résultat-retenu / résultat-non-retenu racontent l'**indiscernabilité** en une image.
- **Describe B — remplacement post-publication vu CÔTÉ CANDIDAT** (3 tests serial) : quota réduit à 2 par SQL → l'admin calcule → publie → déclare Awa indisponible (Mariam promue) ; **login candidat Awa** → « Votre candidature a été clôturée », DOM sans score/rang/mention du remplacement (capture) ; **login candidat Mariam** → « retenue », indiscernable d'une retenue de première heure (capture). Complète `actes-exceptionnels.spec.js` (8d-3), qui ne testait que le côté admin.

**Friction d'intégration découverte (l'objet même de ce lot).** `parcours-candidature.spec.js` — et donc **aucun E2E de wizard jusqu'ici** — soumettait un dossier **silencieusement `non_eligible`** : la réponse `sc05 = 'oui'` (« bénéficiaire ACTUEL d'un programme de formation ») est un **critère éliminatoire** (`ServiceEligibilite::evaluerSoumission`, SC.05). La réponse HTTP de `/soumettre` étant **neutre par conception** (règle reine — identique éligible ou non), le test ne voyait rien : il ne vérifiait que le 200 + l'écran « déjà soumise ». **Aucun test n'avait donc jamais prouvé qu'un candidat va jusqu'à `retenu`.** Ce n'est **pas un bug** (le neutre est voulu, ADR-03) — c'est un **trou de couverture E2E**, comblé : `integration.spec.js` répond `sc05 = Non` / `sc06 = Non` et **assert `statut_interne = 'soumis'` en base** juste après le wizard (la seule façon de constater l'éligibilité, la réponse ne la disant pas). `parcours-candidature.spec.js` n'est pas corrigé (il passe, hors périmètre) mais le piège est documenté dans son helper.

**Détail — mot de passe du candidat frais.** Les comptes démo (`Demo2026!`, 9 caractères) sont seedés directement et **contournent** la validation d'inscription. Un candidat qui s'inscrit *pour de vrai* passe `Password::min(10)->letters()->numbers()->mixedCase()` — `Demo2026!` serait **refusé**. `integration.spec.js` utilise `MotDePasse2026` pour le candidat frais, `Demo2026!` pour les comptes démo (`login()` prend le mot de passe en paramètre).

**Conséquence.** Aucun changement de code applicatif (backend ni frontend `src/`). **Bilan de santé consolidé, stack Docker complète, tout vert (697 tests) :** `php artisan test` **303** (1593 assertions) · `vitest` **321** (29 fichiers) · E2E par-espace `npm run e2e` **64** (desktop + mobile, 9 specs) · E2E intégration `npm run e2e:integration` **9** (parcours nominal 6 + remplacement côté candidat 3). Captures direction (`e2e/__screenshots__/integration-*`) : `soumission`, `en-cours`, `publication-friction` (le modal avec la saisie du nom), `resultat-retenu` **vs** `resultat-non-retenu` (l'indiscernabilité en une image), `remplacement-sortant`, `remplacement-promu` — 390/1280.

**Divergences maquette.** Aucune (lot de vérification, pas de nouvelle surface).

## ADR-27 — Durcissement sécurité + configuration de production (Lot 9b)

**Contexte.** L'app tourne en dev sur `localhost:8080`, HTTP nu, `SESSION_DOMAIN=localhost`, cookies non-`Secure`, aucun en-tête de sécurité. Il faut la rendre **déployable en sécurité** sur un serveur Ubuntu avec un domaine réel + HTTPS, **sans rien coder en dur** (domaine, chemins de certificats, secrets = tous paramétrables) et **sans casser le dev** (localhost reste utilisable).

**Constat structurant.** `config/session.php` et `config/sanctum.php` lisent **déjà tout via `env()`** (`session.secure`, `session.same_site`, `session.domain`, `sanctum.stateful`…). La bascule prod = **uniquement des valeurs**, aucun code de config à toucher. Seul fichier de code modifié : `bootstrap/app.php` (cf. `trustProxies`).

**Décision.**
- **Override compose, pas de duplication.** `docker-compose.prod.yml` n'exprime **que les différences** — lancé `-f docker-compose.yml -f docker-compose.prod.yml`. `docker-compose.yml` (dev) reste **byte-identique**. Les listes `volumes`/`ports` sont remplacées via le tag Compose `!override` (v2.24+) : backend perd le bind-mount du code (image figée) + gagne `env_file: backend/.env.production` ; nginx perd `8080:80`, gagne `80:80`+`443:443`, la conf de prod, les montages TLS + webroot ACME ; postgres exige `POSTGRES_PASSWORD` (`:?`, pas de défaut faible).
- **TLS terminé dans le conteneur nginx** (architecture inchangée : un seul point d'entrée). Conf de prod (`docker/nginx/casa.prod.conf`, montée PAR-DESSUS la conf dev) **sans aucune valeur en dur** : `server_name _` (l'app est le seul vhost, les redirections utilisent `$host`) ; chemins de certificats **FIXES DANS LE CONTENEUR** (`/etc/nginx/tls/{fullchain,privkey}.pem`), le contenu vient du montage `${TLS_DIR}:/etc/nginx/tls:ro`. `:80` → **301** `https://` sauf `/.well-known/acme-challenge/` (renouvellement webroot à chaud). `:443` : TLS 1.2/1.3, ciphers modernes, `http2 on`, OCSP stapling (no-op tant que self-signed).
- **Certificat : certbot sur l'HÔTE Ubuntu** (`apt install certbot`, `--webroot`, timer systemd pour le renouvellement, `--deploy-hook` = `docker/nginx/renew-hook.sh` qui copie les fichiers PLATS dans `${TLS_DIR}` — pas les symlinks de `live/` — et recharge nginx). Domaine **toujours en variable** (commande certbot + hook), jamais dans la conf nginx. **Variante conteneurisée** (service `certbot` dans compose) écartée : plus de pièces mobiles, moins standard sur Ubuntu. **Cert de bootstrap self-signed** (`docker/nginx/gen-selfsigned.sh`, `${TLS_DIR}` gitignoré) pour amorcer nginx avant Let's Encrypt (œuf/poule ACME).
- **6 en-têtes de sécurité** (bloc HTTPS, `add_header … always` → aussi sur les 4xx/5xx) : `Strict-Transport-Security` (1 an + `includeSubDomains`, sans `preload`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/micro/géo/paiement/usb `= ()`), **CSP**.
- **CSP stricte** — app 100 % vendored (npm), **aucun CDN à autoriser**. `script-src 'self'` **STRICT** (`dist/index.html` = 1 `<script src>` + 1 `<link>`, zéro inline). Deux relâchements, **tous deux sans vecteur d'exécution de code** : `style-src 'unsafe-inline'` (les attributs `style={{…}}` React — CSP `style-src` gouverne aussi les attributs `style=`) et `font-src data:` (Vite inline les sous-jeux de police < 4 Ko — `@fontsource` vietnamien/cyrillique, `fa-v4compatibility` — en `data:` dans le CSS bundlé ; découvert par le test navigateur, `font-src 'self'` seul bloquait le rendu). `img-src 'self' data:`, `connect-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`.
- **`bootstrap/app.php` — `$middleware->trustProxies(at: env('TRUSTED_PROXIES', '*'))`.** Dans CETTE topologie, nginx est le SEUL edge : il passe déjà `REMOTE_ADDR = $remote_addr` (IP client réelle) et `HTTPS=on` en **fastcgi_param** (non forgeables) → `$request->secure()` correct **nativement**, sans `trustProxies`. C'est donc du **durcissement / une préparation** à une LB ou un CDN en amont. `'*'` est sûr ici (`backend:9000` non publié, joignable uniquement par nginx qui **écrase** `X-Forwarded-For` — jamais d'append → non-spoofable). **`.env.production.example` pousse FORTEMENT à resserrer `TRUSTED_PROXIES` au sous-réseau Docker** (impacte l'IP tracée à l'audit ADR-12 et le rate-limiting). No-op en dev (aucun en-tête forwarded sur `/api`).
- **`APP_DEBUG=false`** (fixé dans l'`.example`) : un vrai 500 renvoie `{"message":"Server Error"}` — **ni trace, ni chemin, ni SQL** (prouvé). `LOG_CHANNEL=stderr` (12-factor, `docker compose logs`).
- **Pièces hors webroot (ADR-11) confirmé + durci** : `storage/app/private/` est hors du `root` nginx ; les seuls `location` avec `root` sont `/api|/sanctum|/up` → `index.php`. Ajout de `location ~ /\. { return 404; }` et `location ^~ /storage/ { return 404; }` — sans quoi ces chemins retombaient sur le fallback SPA (`index.html`, 200 : inoffensif mais trompeur pour un scanner).
- **Secrets** : `.env.production` (racine) + `backend/.env.production` **gitignorés** (`.gitignore` complété : `/.env.production`, `/.env.prod`, `/backend/.env.prod`, `docker/nginx/tls/*`, `docker/nginx/acme-webroot/*`). `backend/.dockerignore` **créé** (absent avant) : `.env*` (sauf `.env.example`), `.git/`, `tests/`, `phpunit.xml`, `storage/*`, `bootstrap/cache/*` → aucun secret ni test dans l'image.
- **Le build frontend est domaine-agnostique** : `VITE_API_URL=/api` **relatif** → la MÊME image sert dev et prod, **aucun rebuild par domaine**.

**Conséquence.** Un seul fichier de code applicatif touché (`bootstrap/app.php`, no-op en dev). **Preuve prod-like** (`docker-compose.prod.yml`, `DOMAIN=casa.localhost`, cert self-signed) : `scratchpad/prodlike9b.sh` **31 OK / 0 FAIL** — 301 http→https, SPA en HTTPS, les 6 en-têtes sur `/` ET `/api`, cycle Sanctum derrière TLS (cookies `Secure`, login admin + acte mutant → 200), 500 sans fuite, `/storage` + `/.env` → 404 ; **+ test navigateur** (Playwright, HTTPS) : SPA rendue, styles appliqués, login navigateur OK, **zéro violation CSP**. Non-régression dev : `npm run lint` vert, `vitest` auth/lib/routing **26/26**, backend auth/middleware/rôles/téléchargement **36/36** (144 assertions) — `trustProxies` confirmé no-op en dev.

**Point ouvert.** HSTS `preload` (soumission à hstspreload.org) — à décider séparément (engageant, difficilement réversible). `config:cache`/`route:cache` en prod (perf) → runbook 9c. Infra mail (`MAIL_MAILER=log` aujourd'hui) → hors CASA.

**Divergences maquette.** Aucune (infra).
